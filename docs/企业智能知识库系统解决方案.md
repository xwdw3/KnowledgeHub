# 私有化企业智能知识库系统 解决方案

> 文档定位：项目立项 / 技术方案 / 答辩评审材料
> 技术路线：RAG（Retrieval-Augmented Generation）检索增强生成
> 版本：v1.0　｜　对齐代码快照：`E:/knowledge`（src/main.py、src/query_rag.py、src/ingest.py）

---

## 1. 项目背景

### 1.1 企业知识管理的三层困境

| 层级 | 现状 | 具体表现 |
| --- | --- | --- |
| 存储层 | 知识分散 | 制度文件在 OA 附件、业务文档在共享盘、技术资料在个人电脑与聊天记录中，无统一入口 |
| 检索层 | 查找低效 | 依赖文件名与关键词精确匹配，无法理解语义（搜"报销上限"找不到《差旅费用管理办法》） |
| 应用层 | 难以沉淀 | 老员工离职带走经验，重复性提问反复耗费人力，知识复用率极低 |

### 1.2 通用大模型的四个不可用

| 缺陷 | 影响 | 业务后果 |
| --- | --- | --- |
| 数据无法私有化 | 敏感内容需上传公有云 | 违反数据合规要求，涉密制度不可外发 |
| 回答幻觉严重 | 凭训练记忆"合理编造" | 引用错误条款，误导决策，责任无法追溯 |
| 无法对接私有资料 | 训练数据不含企业内部文档 | 对内部问题只能给出通用空话 |
| 安全性差 | 无数据隔离、无审计 | 无法满足权限管控与可追责要求 |

**结论**：直接使用通用大模型无法落地企业知识库场景，必须"私有化部署 + 私有知识驱动的精准生成"。

## 2. 建设目标

### 2.1 总目标

基于 RAG 技术搭建**私有化、可管控、可追溯**的企业智能知识库系统，实现企业知识的结构化沉淀与智能化问答。

### 2.2 量化指标

| 维度 | 指标 | 目标值 |
| --- | --- | --- |
| 检索效果 | 日常业务问题 Top-5 召回命中率 | ≥ 90% |
| 回答质量 | 答案可溯源率（带原文引用） | 100% |
| 响应性能 | 缓存命中场景响应时间 | < 200 ms |
| 响应性能 | 完整 RAG 问答平均响应时间 | < 5 s |
| 覆盖能力 | 支持的文档格式 | txt / md / pdf / docx（可扩展） |
| 系统稳定性 | 核心链路可用性 | ≥ 99.5% |
| 安全合规 | 知识访问全部经过权限过滤 | 100% |

### 2.3 建设范围

- **支撑层**：知识入库（解析 / 清洗 / 切片 / 向量化）、混合检索、重排
- **应用层**：智能问答（Agent 工具调用）、原文溯源、多轮会话
- **管理能力**：文档生命周期管理、权限标签管控、缓存加速、日志监控

## 3. 总体架构

### 3.1 分层架构

```
┌──────────────────────────────────────────────────────────────────┐
│  接入层   Web 问答工作台 │ 上传/删除控制台 │ REST API │ (可扩展)企微/钉钉 │
├──────────────────────────────────────────────────────────────────┤
│  应用层   FastAPI 服务  输入校验 → 会话管理 → 缓存 → Agent 编排       │
│          多轮会话上下文  │  原文引用与溯源  │  熔断保护              │
├──────────────────────────────────────────────────────────────────┤
│  引擎层   ① 文档解析与切片（RecursiveCharacterTextSplitter）          │
│          ② 混合检索：向量召回 + BM25 + RRF 融合                        │
│          ③ Rerank 精排（BGE-Reranker）                               │
│          ④ LLM 生成（DeepSeek，Function Calling 驱动检索）             │
├──────────────────────────────────────────────────────────────────┤
│  数据层   Qdrant 向量库（chunk + 权限标签） │ PostgreSQL（文档元数据）  │
│           文件存储（原始文档） │ 本地/Redis 缓存 │ 日志文件            │
├──────────────────────────────────────────────────────────────────┤
│  基础设施  Docker Compose 私有化部署    │  Embedding：BGE-M3（1024 维）  │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 关键设计取舍

| 设计点 | 选择 | 理由 |
| --- | --- | --- |
| 生成模型 | DeepSeek（OpenAI 兼容接口） | 中文能力强、成本低、便于切换私有化模型 |
| 向量模型 | BGE-M3（1024 维） | 中文语义检索效果好，支持长文本 |
| 向量库 | Qdrant | 原生支持 payload 过滤，权限过滤可在检索阶段下推 |
| 元数据库 | PostgreSQL | 文档元数据可靠、可审计、可做统计 |
| 检索策略 | 向量 + BM25 混合 | 向量解决"语义相似"，BM25 解决"专有名词/编码精确匹配" |
| 融合算法 | RRF | 无参数、对异构分数量纲不敏感，融合稳定 |
| 生成策略 | Agent 工具调用（而非常规 RAG 管道） | 模型自主决定"是否检索、检索什么"，支持计算类工具与多轮追问 |

## 4. 核心流程设计

### 4.1 知识入库流程

```
上传文档 → 类型白名单校验(.txt/.md/.pdf/.docx)
        → 文本抽取（pypdf / python-docx）
        → 文本清洗（去页眉页脚、空行、乱码，空内容拦截）
        → 语义切片（chunk_size=450~500，overlap=80，按段落/句号递归切分）
        → 批量向量化（BGE-M3，1024 维）
        → 写入 Qdrant（payload：text / file_name / perm 权限标签）
        → 写入 PostgreSQL（document 表：file_name、chunk_count、入库时间）
        → 返回入库结果（分片数量）
```

入库要点：
- **切片策略**：优先按 `\n\n`、`\n`、`。`、`；` 递归切分，保证语义完整性；overlap 保留上下文重叠，避免答案被切断。
- **权限标签随行**：每个 chunk 自带 `perm` 字段，为后续检索阶段的权限过滤提供依据，实现"知识分权"从源头落地。
- **文档可删除**：按 `file_name` 删除时，同步清理 Qdrant 中该文档全部 chunk 与 PG 元数据，保证知识库一致性。

### 4.2 问答流程

```
用户提问
  → 输入校验（非空、长度 ≤1000 字符、非法控制字符拦截）
  → 会话恢复（session_id 维度的多轮历史）
  → 缓存查询（命中则直接返回，< 200ms）
  → Agent 主循环（最多 3 轮，防迷失熔断）
       ├─ LLM 判断是否需要检索
       ├─ knowledge_search：混合检索知识库
       └─ calculate：数值表达式计算
  → 拼接上下文 → LLM 生成答案（带原文引用）
  → 写回缓存 + 会话历史 + 全链路日志
  → 返回答案与来源片段
```

### 4.3 混合检索流程（核心）

```
query
 ├─ 向量召回：Qdrant query_points，携带 perm 权限过滤，limit = RERANK_TOP_CANDIDATE
 └─ 关键词召回：对候选集构建 BM25 索引，计算 BM25 分数
        ↓
 RRF 融合：score = 1 / (k + rank + 1)，k 取经验值，输出融合序列
        ↓
 Rerank 精排：BGE-Reranker 对 (query, chunk) 打分，取 Final Top-K
        ↓
 上下文拼接 → 送入 LLM
```

**为什么是"混合 + 重排"三层？**

| 阶段 | 解决的问题 | 单独使用的短板 |
| --- | --- | --- |
| 向量召回 | 同义表达、语义近似（"差旅报销标准"≈"出差费用额度"） | 对编号、专有名词、精确短语不敏感 |
| BM25 | 关键词精确命中（制度编号、项目代号、人名） | 无法理解同义改写，中文分词依赖 |
| RRF 融合 | 两种召回结果互补，稳定合并 | 只做排序位次融合，不判断语义相关度 |
| Rerank | 交叉编码器逐对精判，把真正能回答问题的片段提到前面 | 计算开销大，只适合对少量候选做 |

> 实践效果：单路向量召回常见问题是"召回得到、但没有排在最前"，导致 LLM 读到噪声上下文而走偏。增加 Rerank 后，上下文纯净度显著提升，答案准确率与可引用性同步改善。

### 4.4 权限管控设计

| 层级 | 控制手段 |
| --- | --- |
| 数据层 | 每个 chunk 携带 `perm` 权限组标签，入库时由上传者的组织/部门属性赋值 |
| 检索层 | 检索请求携带当前用户的权限组，作为 Qdrant `Filter` 的 must 条件**在检索时下推**（非检索后过滤） |
| 应用层 | 会话绑定用户身份，历史上下文不跨用户共享 |
| 审计层 | 记录提问人、检索到的文档、最终答案，支持事后追溯 |

**关键点**：权限过滤必须是**检索阶段下推**，而不是召回后再删除。否则无权限内容已进入上下文，存在被模型间接泄露的风险。Qdrant 的 payload filter 恰好支持这一模式，这是选型 Qdrant 的重要理由。

### 4.5 缓存加速设计

| 缓存对象 | 策略 | 预期收益 |
| --- | --- | --- |
| 高频问题答案 | 问题语义归一化后做 key，TTL 级联失效 | 热点问题响应 < 200ms，LLM 调用成本下降 |
| Embedding 结果 | 文本哈希做 key，本地 LRU | 重复切片/重复提问不再重复计费 |
| 会话历史 | session_id 维度内存存储 + 定期落盘 | 多轮对话无需查库 |
| 文档元数据 | PG 侧索引 + 短 TTL 内存缓存 | 列表类页面秒开 |

缓存失效规则：文档增删改 → 该文档相关缓存与向量同步失效，避免"更新了文档但答案没变"。

### 4.6 日志监控设计

| 监控对象 | 采集指标 | 告警阈值示例 |
| --- | --- | --- |
| 接口层 | QPS、P95/P99 延迟、错误率 | 错误率 > 1% 告警 |
| 检索层 | 召回条数、Rerank 前后差异、空召回率 | 空召回率 > 10% 告警 |
| 生成层 | 首 token 延迟、总耗时、token 消耗、熔断次数 | 熔断次数突增告警 |
| 数据层 | Qdrant 点数、PG 连接数、入库失败率 | 入库失败立即告警 |
| 安全 | 越权访问尝试、超长/非法输入拦截记录 | 出现即告警 |

日志规范：统一结构化输出（时间、会话 ID、用户、问题、检索文档、耗时、状态），既用于排障，也作为知识库运营分析的数据源（哪些问题问得多、哪些文档从没被召回）。

> 兼容性说明：所有模型能力均通过**标准 OpenAI 兼容接口**调用，私有化时可平滑替换为本地部署的 BGE-M3 / Reranker / Qwen 等模型，无需改动业务代码。

## 7. 关键实现要点（含踩坑与对策）

1. **Agent 防迷失熔断**
   模型可能反复调用同一工具、同一参数，陷入死循环。方案：限制最大工具轮次（3 轮）+ 相同 `(工具名, 参数)` 重复调用检测，触发即熔断并给出兜底回答，避免无限消耗与请求超时。

2. **Rerank 异常降级**
   重排服务是外部依赖，异常时不能让问答整体失败。方案：捕获异常后直接返回原始候选顺序，保证可用性优先；同时记录告警日志，便于发现模型服务异常。

3. **上下文纯净度**
   检索结果直接拼接会引入噪声与重复片段。方案：空文本剔除、Top-K 收敛、按相似度截断，并在日志中打印完整上下文，便于复盘"答案为什么这么答"。

4. **输入安全校验**
   空问题、超长输入（>1000 字符）、控制字符会拖慢甚至污染链路。方案：接口层统一拦截，返回明确错误信息，不进入检索与生成环节。

5. **数据一致性**
   文档删除必须"向量 + 元数据"双写一致，否则会出现 PG 有条目、检索却查不到（或反之）的幽灵文档。

6. **Prompt 约束幻觉**
   系统提示明确"仅依据工具返回内容作答、无法确定时明确说明不知道、引用需指明来源文件"，从生成侧抑制编造。

## 8. 部署方案

```
依赖服务：Qdrant（6333） + PostgreSQL（5432）
应用服务：FastAPI（8000），通过 .env 注入模型密钥与库连接

docker compose up -d    →  qdrant / postgres / rag-api 三容器就绪
访问 http://localhost:8000  →  Web 工作台
健康检查 GET /api/health    →  {"status":"ok","code":200}
```

**私有化增强建议**
- 模型层：Embedding / Reranker / LLM 全部换为内网部署版本，仅需修改 `BASE_URL` 与模型名
- 网络层：仅暴露 API 网关，Qdrant 与 PG 不对外
- 数据层：Qdrant 快照 + PG 定期备份，支持知识库整体迁移
- 密钥管理：`.env` 纳入密钥管理系统，禁止入库 Git（`.gitignore` 已配置）

## 10. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 文档质量差（扫描件、乱码、表格错位） | 检索召回失效 | 入库前质量校验 + OCR 预处理；质量不达标文档标记待修复 |
| 切片粒度不当 | 答案被截断或上下文冗余 | 按文档类型分策略切片；建立评测集做 A/B 对比 |
| 模型幻觉 | 误导用户 | 强制引用、置信度不足时拒答、关键条款人工复核机制 |
| 外部模型服务不稳定 | 问答失败或超时 | 重试 + 降级 + 多供应商备份；核心场景本地模型兜底 |
| 权限配置错误 | 越权泄露 | 默认拒绝原则（无权限标签即不可检索）+ 定期权限审计 |
| 成本失控 | LLM 调用费用高 | 缓存命中率监控、上下文长度控制、模型分级路由 |

## 12. 附录：核心接口清单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | Web 问答工作台 |
| POST | `/api/upload` | 上传文档并入库 |
| POST | `/api/ingest` | 入库接口（供测试脚本调用） |
| POST | `/api/delete_doc` | 按文件名删除文档 |
| POST | `/api/chat` | 智能问答（多轮会话） |
| POST | `/api/query` | 仅检索，返回召回片段 |
| GET | `/api/health` | 健康检查 |
