## 三、AC-P3-01：JWT 鉴权与三角色 RBAC

### 3.1 为什么不是"用 JWT 替换 API Key"

企业里有两类调用方，需求正好相反：

- **人**（运营、客服、法务）需要一个账号，能登录、能被追责、离职要能立刻停用 → **JWT**
- **系统**（定时同步脚本、上游业务系统、CI）没有"登录"这个动作，也不该保存会过期的密码 → **API Key**

因此设计为**双通道并存**，中间件按 token 形状判别（三段点分为 JWT，`rag_` 前缀单段为 API Key），不做试错式回退：

```python
def is_jwt(token: str) -> bool:
    """JWT 恒为三段点分；API Key 是 `rag_` 前缀单段。用形状判别，不试错。"""
    return token.count(".") == 2 and not token.startswith("rag_")
```

### 3.2 三角色与权限点

| 角色 | 中文名 | 权限点 |
| --- | --- | --- |
| `admin` | 管理员 | 全部 7 项 |
| `kb_admin` | 知识库管理员 | `kb:read` `kb:write` `kb:admin` `space:admin` |
| `user` | 普通用户 | `kb:read` |

权限点全集：`kb:read` / `kb:write` / `kb:admin` / `space:admin` / `audit:read` / `user:admin` / `metric:read`

**旧角色名兼容**是硬要求：P2 已在用的 `editor` / `viewer` 不能因为升级而 422。

```python
ROLE_ALIASES = {"editor": "kb_admin", "viewer": "user"}
```

验收已验证：用 `viewer` 创建密钥返回 200，落库角色为 `user`；用 `editor` 创建返回 200，落库为 `kb_admin`。

### 3.3 JWT 实现的安全细节

不引入 PyJWT，自研 HS256（零依赖，符合私有化交付"少一个包少一个供应链风险"的原则），但安全底线一条不减：

| 防护点 | 做法 | 为什么必须有 |
| --- | --- | --- |
| 算法混淆攻击 | 显式校验 `alg == "HS256"`，拒绝 `none` | 否则攻击者可改头部为 `alg=none` 伪造任意身份 |
| 签名比较时序攻击 | `hmac.compare_digest` | 普通 `==` 会在首个不同字节返回，可被逐字节爆破 |
| 时间声明校验 | 校验 `iat` / `nbf` / `exp` / `iss`，允许 30s 时钟偏移 | 多实例时钟不同步会导致正常 token 被误判过期 |
| 注销即时生效 | 只把 `jti` 写入黑名单，TTL = token 剩余有效期 | token 本身无状态，不记黑名单就无法"立刻踢人" |
| refresh 重放 | **一次性轮换**：旧 refresh 用过立即进黑名单 | 否则被盗的 refresh 可在 7 天内无限续期 |
| 密钥持久化 | 首次生成写入 `data_v2/jwt_secret`，权限 0600 | 不持久化则容器重建后全员被强制重登 |
| payload 最小化 | 只放 `uid` / `name` / `role` / `spaces` | JWT 是 base64 明文，绝不能放密码或敏感属性 |

## 四、AC-P3-02：知识库空间隔离

### 4.1 核心设计：空间与权限组**正交**

这是 P3 最容易做错的地方，也是最容易被"看起来能用"掩盖的地方。

| 概念 | 回答的问题 | 归属 | 取值举例 |
| --- | --- | --- | --- |
| **权限组**（`perm_group`） | 这个人**能看哪些密级**的内容 | 人的属性 | `hr` / `finance` / `all` |
| **空间**（`space_id`） | 这份内容**属于哪个业务域** | 内容的属性 | `default` / `hr_zone` / `rd_zone` |

两者恰好常取同名值（都用 `hr`），但**绝不能互相赋值**：

- 把权限组当空间用 → P2 存量密钥（`perm_group=hr`）会被判"无权访问 default 空间"，**升级后所有上传与检索 403**
- 把空间当权限组用 → 同一空间内 `hr` 密级文档对所有能进该空间的人都可见，**权限组隔离形同失效**

代码层面用一个显式字段把它们分开：

```python
@dataclass(frozen=True)
class Principal:
    perm_groups: Tuple[str, ...]      # P2：谁能看（来自 API Key 的 perm_group）
    spaces: Optional[Tuple[str, ...]] # P3：能进哪些业务域（来自 users.spaces）
    # API Key 没有 spaces 字段 → None，表示"不额外限制空间，只受权限组约束"
```

### 4.2 三层下推：缺一层等于没隔离

隔离不能只在接口层加个 `if`，必须三层同时下推，否则总有链路绕过：

| 层 | 实现 | 不做会怎样 |
| --- | --- | --- |
| **元数据层** | `documents.space_id` + SQL `WHERE space_id = ANY(...)` | 文档列表、统计、删除接口全部跨空间泄露 |
| **向量层** | Qdrant payload `space_id` + `FieldCondition` 过滤 | 检索能召回别的空间片段——这是最致命的，因为**答案会直接说出来** |
| **缓存层** | 缓存 key 纳入空间列表 | A 部门问过的问题，B 部门直接命中缓存拿到 A 的答案 |

缓存 key 的通配归一化尤其容易漏：

```python
def _space_part(spaces) -> str:
    """通配必须归一成同一标记：`*`/`all`/`None` 语义都是"全部空间"，
    按原样拼进 key 会让同一份结果各存一份，命中率被人为压低。"""
    if spaces_wildcard(spaces):
        return "*"
    return ",".join(sorted(spaces or []))
```

统一判据 `SPACE_WILDCARDS = {"*", "all"}` 供所有下推层复用——**只认 `*` 会导致管理员密钥（`perm_group=all`）反而无权投放文档**，这是本项目实际踩过的坑。

### 4.3 同名文件不互相覆盖

`doc_id` 的哈希必须把空间纳入，否则「人事空间/考勤制度.md」和「研发空间/考勤制度.md」会算出同一个 ID，后上传的把先上传的整份覆盖掉：

```python
def _new_doc_id(file_name: str, space_id: str = "") -> str:
    """空间必须进哈希：否则同名文件会算出同一个 doc_id，后上传的覆盖先上传的。"""
    return uuid.uuid5(uuid.NAMESPACE_URL, f"doc:{space_id}:{file_name}").hex[:16]
```

## 五、AC-P3-03：Redis 缓存层增强

P3 给 Redis 增加了三类**必须共享**的状态。判断标准很简单：多实例部署时，这个状态能不能各存一份？不能共享的就必须进 Redis。

| 能力 | 为什么必须共享 | 实现要点 |
| --- | --- | --- |
| 对话上下文缓存 | 用户第二轮请求可能打到另一个实例 | `TTL 30min`，只留最近 8 轮；**Redis 为准，PG 兜底** |
| Token 黑名单 | 注销操作要立刻在所有实例生效 | 只存 `jti`，TTL = token 剩余有效期；本地副本零延迟优先查 |
| 限流计数器 | 各实例独立计数 = 限流阈值×实例数，等于没限 | 固定窗口 `INCR + EXPIRE` 原子 pipeline |

### 5.1 限流的三个关键决策

**① 身份优先用已认证用户，而非 IP**

```python
# 限流放在认证之后：优先用已认证身份计数，避免攻击者靠换无效 token 绕过
identity = principal.actor if principal else f"ip:{request.state.client_ip or 'unknown'}"
```

**② 必须用 `INCR + EXPIRE` 原子组合**

```python
def incr_with_ttl(self, key: str, ttl: int) -> Optional[int]:
    """必须用 INCR + EXPIRE 的原子组合：先 GET 再 SET 会在并发下丢计数。"""
    pipe = self.client.pipeline(); pipe.incr(key); pipe.ttl(key)
    count, cur_ttl = pipe.execute()
    if cur_ttl is None or cur_ttl < 0:
        self.client.expire(key, max(int(ttl), 1))
    return int(count)
```

**③ 超限不抛异常，返回结构化判定**

中间件根据判定结果自己组装响应，避免"异常被全局处理器改写成 500"：

```python
resp.headers["Retry-After"] = str(verdict["reset"])      # 告诉客户端什么时候可重试
resp.headers["X-RateLimit-Limit"] = str(verdict["limit"])
resp.headers["X-RateLimit-Remaining"] = "0"
```

### 5.2 惰性重连：Redis 挂了不能让进程永久降级

启动时 Redis 未就绪（compose 里 `service_healthy` 之前偶尔抢跑）会把整进程钉死在 L1，命中率指标再也不会出现 `l2_hit`：

```python
def _ensure(self) -> bool:
    """降级后每 15 秒允许探活一次，Redis 恢复即自动回到 L2。"""
    if self.available and self.client:
        return True
    now = time.time()
    if now - getattr(self, "_last_retry", 0) < 15:
        return False
    self._last_retry = now
    self._init_client()
    return self.available
```

### 6.1 两条输出通道，职责不同

| 格式 | 给谁看 | 用途 |
| --- | --- | --- |
| **JSON 单行** | Filebeat / Loki / ELK | 按字段建索引，不需要正则抠日志 |
| **文本** | 人（`docker logs`） | 一眼看到 trace_id 串起的时序 |

通过 `LOG_FORMAT=json|text` 切换，业务代码完全一致。默认 json，因为交付形态是容器。

### 6.2 实测日志样例

```json
{"ts":"2026-10-17T16:40:56.223","level":"INFO","logger":"access",
 "trace_id":"641f46ac165d","message":"POST /api/v1/chat -> 200 (1523ms)",
 "event":"access","method":"POST","path":"/api/v1/chat","query":"",
 "status":200,"latency_ms":1522.8,"user_id":"admin","role":"admin",
 "client_ip":"127.0.0.1","user_agent":"Python-urllib/3.11"}
```

P3 要求的四项埋点全部到位：**请求ID（trace_id）、用户ID（user_id）、接口耗时（latency_ms）、异常堆栈（异常时进 `stack` 字段）**。

### 6.3 敏感信息脱敏：靠机制而不是靠自觉

日志泄露密钥是最高频的安全事故之一。用递归脱敏，按 key 名匹配，**人工 review 每一条 log 语句不现实**：

```python
_SENSITIVE_KEYS = ("password", "passwd", "pwd", "secret", "token", "authorization",
                   "api_key", "apikey", "access_key", "private_key",
                   "credential", "cookie", "session")

def redact(obj, depth=0):
    """递归脱敏。depth 上限防止病态嵌套结构把日志打爆。"""
    if isinstance(obj, dict):
        return {k: ("***" if any(s in k.lower() for s in _SENSITIVE_KEYS)
                    else redact(v, depth + 1)) for k, v in obj.items()}
    ...
```

**实测取证**：对全部容器日志执行敏感词扫描

```
$ docker logs rag_p3_api 2>&1 | grep -ciE "rag-admin-p2-2026|Adm1n@2026kb|password\":"
0
```

### 6.4 异常落库：日志是流，会消失；排查发生在之后

日志会被轮转、被采集、7 天后就没了，而线上排查往往发生在"用户报障之后"。因此 5xx 异常必须进 `error_logs` 表，才能按 trace_id 反查：

```sql
CREATE TABLE error_logs (
    id BIGSERIAL PRIMARY KEY, trace_id VARCHAR(64), path VARCHAR(256),
    method VARCHAR(16), user_id VARCHAR(128), status_code INTEGER,
    exc_type VARCHAR(128), message VARCHAR(2000), stack TEXT, created_at TIMESTAMPTZ
);
```

两条路径都要写（中间件捕获 + 全局异常处理器），否则会出现"有 trace_id 但错误表里查不到"的空档。**写错误日志失败绝不能再引发一次错误**，因此整段 `try/except` 吞掉。

**实测取证**：

```

  message  = 自检异常：验证 error_logs 落库链路
```

## 七、AC-P3-05：Prometheus + Grafana 监控

### 7.1 一个刻意的取舍：不引入 exporter

Qdrant / PostgreSQL / Redis 的负载**不靠各自的 exporter**，而由应用侧主动探测后暴露为 `rag_db_*` / `rag_qdrant_*` / `rag_redis_*`。

理由：私有化交付里少装一个组件就少一个运维面、少一个故障点，而应用本来就要连这些组件，探测成本几乎为零。代价是拿不到慢查询明细，但 P3 的监控目标是"QPS / 延迟 / 错误率 / 负载"，这个粒度足够。

探针设计有一条硬约束——**指标采集绝不能反过来给被监控组件加压**：

```python
def load(self) -> dict:
    """只取 O(1) 的命令（INFO / DBSIZE），不做 SCAN：
    指标采集绝不能反过来给被监控组件加压，否则监控本身就成了故障源。"""
```

向量库同理：用 `get_collection` 取近似点数，**不用 `count(exact=True)`**——后者在大集合上会全量扫描，被 Prometheus 每 15 秒打一次等于自己制造负载尖峰。

### 7.2 指标清单

| 分组 | 指标 | 类型 |
| --- | --- | --- |
| 流量 | `rag_requests_total` / `rag_http_requests_total{method,path,status}` / `rag_request_inflight` / `rag_uptime_seconds` | counter/gauge |
| 延迟 | `rag_request_duration_ms{quantile}` / `rag_slow_requests_total` / `rag_llm_latency_ms` / `rag_rerank_latency_ms` | gauge |
| 错误 | `rag_errors_total` / `rag_auth_failures_total` / `rag_forbidden_total` / `rag_rate_limited_total` | counter |
| 数据库负载 | `rag_db_up` / `rag_db_pool_used` / `rag_db_pool_max` / `rag_db_latency_ms` / `rag_db_documents` / `rag_db_chunks` | gauge |
| 向量库负载 | `rag_qdrant_up` / `rag_qdrant_points` / `rag_qdrant_latency_ms` | gauge |
| Redis 负载 | `rag_redis_up` / `rag_redis_used_memory_bytes` / `rag_redis_maxmemory_bytes` / `rag_redis_used_ratio` / `rag_redis_keys` / `rag_redis_evicted_total` | gauge/counter |

## 八、AC-P3-06 / 07：混合检索、Rerank 与答案溯源

### 8.1 检索链路

```
query
  ├─ 向量召回（BGE-M3 1024 维，Qdrant，带 space_id + perm 过滤）
  ├─ BM25 召回（jieba lcut_for_search 分词，本地索引）
  ├─ RRF 融合（k=60）
  ├─ Rerank 重排（候选 10 条 → 三模式）
  └─ 相关度打分 0.45*vec + 0.35*bm25_norm + 0.20*coverage，< 0.25 拒答
```

**为什么需要 RRF 而不是简单加权**：向量分与 BM25 分的量纲完全不同（余弦相似度 vs 词频打分），直接加权需要调参且不稳定。RRF 只看名次，天然免疫量纲问题。

### 8.2 Rerank 三模式

| 模式 | 做法 | 适用场景 |
| --- | --- | --- |
| `off` | 不重排，直接用 RRF 结果 | 回归 P2 行为，压测基线 |
| `llm` | 一次调用批量打分返回 JSON | 效果最好，多一次 LLM 调用 |
| `heuristic` | `0.6×词覆盖 + 0.3×向量分 + 0.1×min(rrf*60, 1.0)` | 零成本零延迟，LLM 不可用时的兜底 |

**LLM 失败必须自动降级**，不能让重排失败拖垮整条问答链路：

```python
try:
    ordered = _llm_rerank(query, candidates)
    ...
except Exception as exc:
    logger.warning("LLM 重排失败，降级为启发式：%s", exc)
    info["fallback"] = f"llm 失败：{type(exc).__name__}"
```

### 8.3 答案溯源

每条引用都带完整来源信息，用户能点回原文核对：

```python
class SourceItem(BaseModel):
    doc_id: str
    file_name: str
    space_id: str          # 哪个业务域
    chunk_index: int
    score: float
    rerank_score: float    # 重排后的相关度

```

答案正文内嵌 `[来源N]` 标记，只标记**实际被引用**的片段，越界编号直接丢弃（不伪造引用）。

## 九、验收过程中发现并修复的缺陷

全部为**真实缺陷**，不是脚本问题。这类问题只有靠"完整回归 + 容器内真实环境"才能暴露。

### 9.1 空间与权限组语义混淆（最严重）

**现象**：P2 回归 A19 失败——`kb_admin(hr)` 密钥上传文档返回 `403 无权在该空间投放文档：default，当前可访问 ['hr']`。

**根因**：P3 引入空间后，代码把 API Key 的 `perm_group` 直接当成 `spaces` 用。存量密钥 `perm_group=hr` 被判为"无权访问 default 空间"，**升级后所有存量密钥的上传与检索全部 403**。

**修复**：在 `Principal` 上显式拆分两个字段，并加注释说明"正交且绝不能互相赋值"：

```python
perm_groups: Tuple[str, ...]               # P2：谁能看
spaces: Optional[Tuple[str, ...]] = None   # P3：能进哪些域；None = 不限制
```

所有空间判断改用 `principal.space_scope`（未绑定空间时返回 `["*"]`），权限组判断保持严格不补 `all`。

### 9.2 JWT 用户权限组取值错误

**现象**：修复 9.1 时发现 `_user_to_principal` 把 `spaces` 直接塞进 `perm_groups`。

**后果**：同一空间内 `hr` 密级文档对所有能进该空间的人都可见，**权限组隔离形同失效**。

**修复**：新增 `_derive_perm_groups(spaces)`，规则为「空间名 ∪ {all}」，通配空间映射为通配权限组：

```python
def _derive_perm_groups(spaces: Tuple[str, ...]) -> Tuple[str, ...]:
    """`*` 空间 → 通配权限组；否则 空间名 ∪ {all}。
    既保证"进了 hr 空间能读 hr 密级文档"，又不会因缺字段读不到公共文档。"""
```

### 9.3 `rag_redis_up` 恒为 0

**现象**：Redis 容器 healthy、`redis.ping()` 返回 True，但 `/metrics` 中 `rag_redis_up 0`。

**根因**：指标代码写的是 `cache_service.l2.load()`，而模块导出的实例名是 `cache`。`ImportError` 被 `_render_dependencies` 的 `except Exception` 吞掉，**静默降级为 0**。

**修复**：改为 `from app_v2.services.cache_service import cache as two_level_cache`。同时全局排查了同类引用，确认其余各处都走模块级函数（`cache_service.xxx()`），只有这一处直接摸实例。

> 这个缺陷的教训是：监控代码里的 `except: pass` 会让"指标挂了"伪装成"组件挂了"，比不监控更危险。修复后已改为显式记录 `error` 字段。

### 9.4 限流规则静默失效

**现象**：`RATE_LIMIT_RULES=/api/v1/chat=30` 配置后不生效，全部请求落回默认阈值 120。

**根因**：Git Bash / MSYS2 把 `/api/v1/chat` 当作 POSIX 路径改写成 `E:/work/WorkBuddy/resources/vendor/PortableGit/api/v1/chat`。

**修复**：不能只剥盘符（会得到 `/work/...`），要**以第一个 `/api/` 或 `/metrics` 为锚点反推**——URL 路径的前缀只可能是这两种起点之一：

```python
@staticmethod
def _normalize_rule_prefix(prefix: str) -> str:
    p = (prefix or "").strip().replace("\\", "/")
    for anchor in ("/api/", "/metrics"):
        idx = p.find(anchor)
        if idx >= 0:
            return p[idx:]
    ...
```

### 9.5 其他小问题

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| `rate_limited` 指标不可见 | `incr()` 走 `setattr`，属性未在 `__init__` 声明会抛 `AttributeError`，被中间件 `try/except` 吞掉 | 显式 `self.rate_limited = 0` |
| 引用片段缺 `space_id` | `_to_source` 未透传 | `SourceItem` 加字段并填充 |
| compose YAML 解析失败 | `environment` 块混用映射与列表 | 统一为映射写法 |
| API 容器启动即 Restarting | 首次 `up --build` 时 API 容器抢在网络就绪前创建，DNS 解析 `postgres` 失败 | `--force-recreate` 恢复；已在 `depends_on` 基础上建议改为重建顺序 |
