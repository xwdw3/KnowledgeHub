## 二、【P1 阶段】RAG 核心链路原型验收

> 阶段目标：验证"文档进来 → 切片向量化 → 检索召回 → 生成带溯源的答案"这条核心业务链路能跑通，并用 Docker Compose 一键启停。详细文档：`05-P1阶段验收文档.md`。

### 2.1 P1 验收标准逐条结论

| 编号 | P1 验收标准 | 结论 | 实测证据 |
|------|------------|------|----------|
| AC-01 | 服务正常启动，无模块报错 | ✅ | 三容器 `healthy`，启动日志无异常栈 |

## 三、【P2 阶段】生产化加固验收

| 编号 | P2 验收标准 | 结论 | 关键证据 |
|------|------------|------|----------|
| AC-P2-01 | 安全：API Key + RBAC | ✅ | 无密钥 401 / 越权 403 / 权限组隔离 / 吊销即时生效 |
| AC-P2-02 | 缓存：L1 LRU + L2 Redis | ✅ | L1 命中 0ms；**重启后跨进程 L2 命中 `l2_hit=1`**；写后自动失效 |

### 3.2 【P2 阶段】修复的工程缺陷（9 项）

全部为"能跑但错"的类型，只有端到端断言才能发现。典型：

- 会话历史接口 500——P1 遗留的响应注解错误，仅在打开 P2 严格校验后暴露；
- 权限组语义、密钥生命周期等 8 项（完整清单见 P2 文档第七章）。

> P2 的经验教训：**验收脚本自身出错时，表现和"功能缺陷"一模一样**。第一次跑 P1 回归时 8 项上传用例全红，实际是被测服务正确返回了 401。定位方法：先 `curl` 手工复现，用真实 HTTP 码对照脚本结果。

## 四、【P3 阶段】多用户协作与可观测验收

> 阶段目标：解决"能不能给多个业务部门同时用、出了问题能不能定位到根因"。详细文档：`07-P3阶段验收文档.md`。

### 4.1 P3 验收标准逐条结论

| 编号 | P3 验收标准 | 结论 | 关键证据 |
|------|------------|------|----------|
| AC-P3-01 | JWT 鉴权 + 三角色 RBAC | ✅ | 登录签发 access+refresh；`alg=none` 被拒；注销后立即失效；admin/kb_admin/user |
| AC-P3-02 | 知识库空间隔离 | ✅ | **元数据/向量/缓存三层同时下推**；跨空间同名不覆盖；越权 404 |
| AC-P3-03 | Redis 缓存层增强 | ✅ | 上下文缓存、Token 黑名单、限流（第 31 次 429）、问答缓存按空间隔离 |
| AC-P3-04 | 全链路结构化日志 | ✅ | JSON 单行含 trace_id/user_id/latency；**密码与密钥 0 泄露** |
| AC-P3-05 | Prometheus + Grafana | ✅ | 抓取 2/2 UP；22 面板 / 5 分组自动装配 |
| AC-P3-06 | BM25+向量混合检索 + Rerank | ✅ | 向量+BM25+RRF 融合；Rerank 三模式，重排 3ms，失败自动降级 |
| AC-P3-07 | 答案溯源 | ✅ | 引用带 doc_id/file_name/space_id/rerank_score；正文内嵌 `[来源N]` |

三套脚本均在 API 容器内针对容器网络执行，走真实 Qdrant/PG/Redis/真实模型：`verify_p3.py` **69/69**（67.7s）、`verify_p2.py` 61/61、`verify_v2.py` 36/36。

### 4.2 【P3 阶段】修复的缺陷（5 组）

1. **空间与权限组语义混淆**（最严重）：两套范围概念互相赋值，升级即越权；
2. JWT 用户权限组取值错误；
3. `rag_redis_up` 恒为 0（监控失真）；
4. 限流规则静默失效；
5. 其他小问题（详见 P3 文档第九章）。

## 五、【P2+P3 阶段】验收标准逐条验证

> 独立于两阶段开发文档，把 P2/P3 的**验收标准原文**逐条对照实测。详细文档：`08-P2P3验收标准验证报告.md`。

| # | 验收标准（原文摘要） | 结论 | 关键证据 |
|---|---------------------|------|----------|
| 1 | 所有接口必须携带 JWT Token，未授权拒绝访问 | ✅ | 18 个端点无凭证一律 401；5 种畸形 token 全拒；`alg=none` 伪造被拒 |
| 2 | 不同角色只能查看授权范围内内容 | ✅ | 空间与密级双维度隔离；缓存 key 含权限维度，预热也不泄露 |
| 3 | 相同问题命中缓存，减少 LLM 调用 | ✅ | 首次 1392~2866ms，重复提问 **0ms 且 cached=true**；LLM 调用计数零增长 |
| 4 | 全链路日志可追溯所有用户操作 | ✅ | `doc.upload`/`chat.query`/`doc.delete` 三类留痕，字段完整 |
| 5 | Grafana 可视化面板 | ✅ | 22 面板/5 分组；6 类指标可查 |
| 6 | 混合检索 + Rerank | ✅ | 单条结果同时携带 vec/bm25/rrf/rerank 四项评分证据 |
| 7 | 知识库问答准确率明显提升 | ✅ | Hit@1 **90%→100%**，MRR **0.950→1.000**，干扰胜出 1/10→0/10 |

**【P2P3 轮】修复的 4 个真实缺陷**：

1. `/auth/token` 把密级当成空间——**所有 P2 存量密钥升级后无法上传**的破坏性变更；
2. `_llm_rerank` 并列退化——LLM 打分并列时等于没重排，加 `_orig_rank` 二级键后准确率达标；
3. 写入范围继承读取范围的 `all`（越权漏洞）；
4. 脚本侧问题（详见 P2P3 报告第八章）。

连跑两轮结果一致，脚本对限流具备自恢复能力。

### 6.4 【P4 阶段】修复的真实缺陷（22 项，按严重度）

**高危 9 项**：

| # | 缺陷 | 后果 |
|---|------|------|
| 1 | 审计表未写 `tenant_id` | B 租户管理员能看见 A 租户全部操作 |
| 2 | claims 租户非法时静默降级 | 静默串户：用户被丢进默认租户看到别人内容 |
| 3 | `/login` 页面返回 401 | 登录页自己需要登录，死循环 |
| 4 | OIDC state 存进程内 | 多副本下登录随机失败 |
| 5 | SSO 票据存进程内 | 多副本下换票失败，被踢回登录 |
| 11 | 任务 payload 键名错配（`size` vs `file_size`） | `use_stream` 恒 False，**GB 级文件也走全量读取，流式链路形同未接** |
| 12 | `_save` 用 `json.dumps` 全量序列化 | GB 级语料 MemoryError（崩在"写 64 字节"这种位置） |
| 13 | `np.vstack` 整表复制扩容 | 峰值 ≈ 3 倍矩阵，GB 级必然 OOM |
| 14 | 离线向量用内置 `hash()` | `PYTHONHASHSEED` 使重启后旧向量全部错位，检索静默劣化 |

**中危 12 项**（#6 告警重复、#7 container_name 写死、#8 缺租户 API、#9 停机窗口、#15 np.load 只读视图、#16 _save 缺 mkdir、#17 savez 落盘峰值翻倍、#18 索引路径后缀歧义、#19 task_routes 覆盖显式队列、#20 KEDA 漏 rag_large、#21 api 缺 PDB、#22 worker 无 startupProbe/滚动策略未反向）+ 低危 1 项（#10 审计队列 kill -9 丢未落库记录）。完整表格见 P4 文档第四章。

> P4 缺陷的共同点：**在"小文件 + 单实例"的验证口径下全部绿灯**。验收口径升级到"GB 级文件 + 集群语义"后它们才现形。第 11 条最典型——功能测试全绿、接口全通，但流式链路从没被真正执行过。

## 七、全项目缺陷汇总（按阶段标注）

| 阶段 | 缺陷数 | 最有代表性的缺陷 |
|------|--------|------------------|
| P1 | 0（验收时无；遗留 5 项风险） | R-05 无鉴权 → 直接催生 P2 |
| **P2** | 9 | 会话历史接口 500（P1 遗留，严格校验后才暴露） |

| **合计** | **40 项** | 全部修复并有回归验证 |

共性规律：**验收标准不是给"功能列表"用的，是给"较真"用的**。每一阶段的缺陷都不会让功能报错——它们只是让系统在真实规模（多用户、多副本、GB 级文件、集群升级）下坏掉。
