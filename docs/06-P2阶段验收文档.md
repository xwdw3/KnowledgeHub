> 验收对象：`p1_prototype/app_v2/`（P2 生产就绪版）
> 阶段目标：补齐**安全、缓存、审计、监控**四项企业上线必备能力

> 验收环境：Docker Compose 四容器（qdrant / postgres / redis / api），`MODEL_MODE=real`

## 一、验收结论总览

P1 只证明"链路能跑通"，P2 要证明"敢放到生产"。四项能力按风险从高到低排列：

| 编号 | 能力 | 生产风险（如果没有） | 结论 | 关键证据 |
| --- | --- | --- | --- | --- |
| AC-P2-01 | 安全：API Key + RBAC | 任何人可调接口，知识库内容全员可见 | ✅ 通过 | 无密钥 401 / 越权 403 / 权限组隔离 / 吊销即时生效 |
| AC-P2-02 | 缓存：L1 LRU + L2 Redis | 同类问题重复走 LLM，成本与延迟线性增长 | ✅ 通过 | L1 命中 0ms；**重启后跨进程 L2 命中 `l2_hit=1`**；写后自动失效 |
| AC-P2-03 | 审计：全链路操作留痕 | 出事后无法追溯谁在何时做了什么 | ✅ 通过 | 35 条留痕（success 28 / denied 7），含来源 IP，写入零丢弃 |
| AC-P2-04 | 监控：Prometheus + 看板 | 故障不可观测，只能等用户投诉 | ✅ 通过 | `/metrics` 标准文本、p50 9.3ms / p99 1579.7ms、`/dashboard` 可视化 |

### 1.2 与 P1 的关系

P1 的 6 项验收标准（服务启动、文档入库、召回生成、Agent 调用、一键启停、环境可复现）在 P2 中**全部回归通过**，未因新增安全层而退化：`scripts/verify_v2.py` 在开启鉴权后 **36/36 通过**。

回归期间额外发现并修复 3 个真实缺陷（详见第七章 7~9 项），其中「会话历史接口 500」是 P1 遗留的响应注解错误，仅在打开 P2 严格校验后才暴露。

### 2.2 容器镜像

| 服务 | 镜像 | 容器名 | 端口映射 | 说明 |
| --- | --- | --- | --- | --- |
| 向量库 | `qdrant/qdrant:v1.12.4` | `rag_p2_qdrant` | 不对外 | 与 `qdrant-client` 1.12.x 严格对齐 |
| 业务库 | `postgres:15-alpine` | `rag_p2_postgres` | 不对外 | 存文档元数据、密钥、审计 |

> **安全设计**：数据组件一律不映射宿主机端口。生产环境即使宿主机防火墙配置失误，向量库/业务库/缓存也不会被外部直连。

### 2.3 Redis 配置要点

```yaml
command: >
  redis-server
  --appendonly no          # 缓存不做 AOF，重启即空（缓存可丢）
  --save ""                # 关闭 RDB 快照，避免 fork 抖动影响主链路延迟
  --maxmemory 256mb        # 内存上限，防止缓存撑爆宿主机
  --maxmemory-policy allkeys-lru
```

**为什么不做持久化**：Redis 在本系统中只承担"减少重复计算"，不是数据源。持久化既不能提升正确性（数据源始终是 Qdrant + PG），又会在重启时引入不一致窗口。关掉持久化后，Redis 挂掉或重启只是缓存变冷，服务功能完全不受影响。

## 三、AC-P2-01 安全：API Key + RBAC

### 3.1 认证失败与公开路径

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 无 `Authorization` 访问 `/auth/me` | 401 | `HTTP=401`，`缺少 Authorization: Bearer <API Key>` |
| 伪造密钥 | 401 | `HTTP=401`，`API Key 无效` |
| 正确密钥 | 200 | `HTTP=200`，返回角色与 6 个权限点 |
| `/metrics` 免鉴权（Prometheus 抓取） | 200 | `HTTP=200` |
| `/api/v1/health`、`/api/v1/ready` 免鉴权（探针） | 200 | `HTTP=200` |

受保护接口的统一错误格式（HTTP 状态码与 `code` 一致）：

```json
{"code": 401, "message": "缺少 Authorization: Bearer <API Key>", "data": null, "trace_id": "cc35349e972d"}
```

### 3.2 角色与权限点

系统内置三角色，权限点为细粒度字符串，便于后续扩展：

| 角色 | 中文名 | 权限点 |
| --- | --- | --- |
| `admin` | 管理员 | `kb:read` `kb:write` `kb:admin` `audit:read` `user:admin` `metric:read` |
| `editor` | 知识编辑 | `kb:read` `kb:write` |
| `viewer` | 只读用户 | `kb:read` |

### 3.3 越权拦截实测

用 `viewer` 密钥尝试各类越权操作，全部被拒且留痕：

| 越权尝试 | 期望 | 实测 |
| --- | --- | --- |
| 创建管理员密钥（提权） | 403 | `403 角色 viewer 缺少权限 user:admin` |
| 读取审计日志 | 403 | `403` |
| 读取指标快照 | 403 | `403` |
| 主动失效缓存 | 403/405 | `405`（方法不允许，等价拦截） |

### 3.4 知识权限组隔离（本轮修复的核心漏洞）

这是 P2 最关键的安全修复。**P1 时代请求体里的 `perm_group` 由调用方自由指定**，等于没有权限控制。P2 改为以密钥绑定的权限组为准。

实测中发现并修复了三个层层递进的问题：

| # | 问题 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | `normalize_perm_groups` 同时被用于"读取可见范围"和"写入目标组" | 上传 `hr` 被存成 `all,hr`，**密件被静默扩大为全员可见** | 拆成两个函数：`normalize_perm_groups`（读，补 all）、`parse_perm_groups`（写，不补） |
| 2 | 密钥解析用 `normalize_perm_groups` | "hr 编辑"认证后变成 `all,hr`，**受限密钥形同全公开密钥** | 认证侧改用 `parse_perm_groups` |
| 3 | 上传校验 `allowed = perm_groups ｜ {"all"}` | 无条件允许投放 `all`，**受限密钥可自我扩权** | 严格子集：`allowed = set(perm_groups)` |

修复后实测：

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| `editor(hr)` 上传到 `all` | 403 | `403 无权将文档归入权限组 all，当前密钥仅限 ['hr']` |
| `editor(hr)` 上传到 `finance` | 403 | `403` |
| `editor(hr)` 上传到 `hr` | 200 且 `perm_group=hr` | `200`，`perm_group=hr`（未被扩写） |
| 管理员上传到 `all` | 200 且 `perm_group=all` | `200`，`perm_group=all` |
| `editor(hr)` 文档列表 | 只见 `hr` 与 `all` | 可见组集合 ⊆ `{hr, all}` |
| `editor(hr)` 删除他人文档 | 403 | 已拦截 |

> **附带修复**：文档列表过滤原先在内存中做，而 `limit` 在 SQL 层先生效，导致"先截断后鉴权"——受限密钥看不到本该可见的高编号文档，且 `total` 与实际不符。已把 `perm_groups` 下推为 SQL 条件（`COALESCE(NULLIF(perm_group,''),'all') = ANY(%s)`），语义正确且减少回传数据量。

### 3.5 密钥生命周期

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 创建密钥返回明文 | 仅此一次，带 `warning` | 返回 `api_key` + `warning` |
| 创建响应是否泄露哈希 | 否 | 不含 `key_hash` / `salt` |
| 密钥列表 | 不含明文 | 5 个密钥，全部无 `api_key` 字段 |
| 吊销自己正在用的密钥 | 422 | `422 不能吊销当前正在使用的密钥` |
| 吊销他人密钥 | 200 | `200` |
| 被吊销密钥立即失效 | 401 | `401`（缓存同步清除，无需等 60s 过期） |
| 已吊销密钥可查询 | 200 | `include_revoked=true` 可见 |

密钥存储：**PBKDF2-HMAC-SHA256，120000 轮，每密钥独立盐**，比对用 `hmac.compare_digest`（常量时间，防时序侧信道）。数据库即使泄露也无法还原明文密钥。

### 3.6 防爆破

同一 IP 在 60 秒窗口内认证失败 5 次即锁定该 IP 的后续认证请求（返回 `认证失败次数过多`）。认证失败次数进入 `/metrics` 的 `rag_auth_failures_total`，可配置告警。

## 四、AC-P2-02 缓存：L1 LRU + L2 Redis

### 4.1 两级结构

```
请求 → L1（进程内 OrderedDict + TTL，2048 条）
        ↓ 未命中
       L2（Redis，跨进程/跨副本共享）
        ↓ 未命中
      真实检索 / LLM 生成 → 回填 L1 + L2
```

**为什么需要两级**：L1 命中耗时 ~1μs，可扛单副本热点；L2 让多副本共享同一份缓存，避免"每个 Pod 各算一遍"。只有 L1 时，扩容反而降低整体命中率。

### 4.2 实测

**分层验证**（同一 query 连续请求，命中层次可分辨）：

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 清缓存后首次检索 | `cached=false`，走完整链路 | `cached=False`，239ms |
| 第 2、3 次检索 | L1 命中，接近 0 延迟 | `cached=True`，0ms，`l1_hit` 累加 |
| **重启 API 后首次检索** | L1 已清空，应命中 L2 | `cached=True`，0ms，`l2_hit=1`，`l1_hit=0` |
| Redis 内实际键值 | 存在且带 TTL | `rag:cache:v1:retrieve:<sha256>`，1050 字节，TTL 286s |
| 主动失效 | 返回清理数量 | `{"l1_removed":2,"l2_removed":2}` |
| 文档写操作后 | 自动失效 | `invalidate_knowledge()` 在增删改后调用 |

> **L2 为什么必须用"重启后命中"来证明**：L1 是进程内缓存，同进程内的重复请求永远先命中 L1，`l2_hit` 恒为 0 —— 这时即使 Redis 完全没工作，用例也会"看起来通过"。只有让 L1 随进程一起消失（重启 API），而 Redis 容器保持运行，此时 `cached=True 且 l2_hit=1` 才能证明跨进程共享真实生效。这是缓存验收最容易做成假绿的地方。

### 4.3 关键设计

| 设计点 | 原因 |
| --- | --- |
| key = 参数排序后 SHA256 | 避免 dict 顺序不同导致同一请求算出不同 key |
| 权限组纳入 key | 否则 A 部门提问命中 B 部门的答案，**缓存层越过越权** |
| TTL 分离：检索 300s / 问答 600s | 问答成本高、时效要求低，可缓存更久 |
| Redis 延迟 `import`，失败自动降级 | Redis 未部署或挂掉时退化为 L1-only，**服务不中断** |
| `delete_prefix` 按类别失效 | 知识库变更只需清 `retrieve:*` 与 `chat:*`，不必全清 |
| L2 命中后回填 L1 | 避免同一热点在进程内反复穿透到 Redis |

## 五、AC-P2-03 审计：全链路操作留痕

### 5.1 异步写入

审计不能拖慢主链路，也不能因审计失败导致业务失败：

```python
_queue = queue.Queue(maxsize=2000)   # 有界队列，防止内存无限增长
# daemon 线程批量消费，队列满时降级为同步写（宁慢不丢）
```

### 5.2 记录内容

| 字段 | 说明 |
| --- | --- |
| `trace_id` | 与响应头 `X-Trace-Id` 一致，可关联全链路日志 |
| `actor` / `role` | 操作人与角色 |
| `action` | 动作，如 `doc.upload` / `chat.query` / `key.create` / `auth.forbidden:kb:write` |
| `resource` | 作用对象，如 `doc:xxx` / `key:xxx` |
| `result` / `status_code` | `success` / `failed` / `denied` + HTTP 码 |
| `ip` / `user_agent` | 来源 |
| `detail` | JSONB，动作相关上下文（文件名、权限组、失效结果等） |
| `latency_ms` | 耗时 |

### 5.3 实测

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 审计日志可查询 | 200 | 35 条（24h 窗口内） |
| 记录问答 | 有 `chat.*` | ✅ `chat.query` |
| 记录密钥创建 | 有 `key.create` | ✅ |
| 记录文档上传 | 有 `doc.upload` | ✅ |
| **越权尝试留痕** | `result=denied` | 7 条（`auth.forbidden:audit:read` / `auth.forbidden:user:admin` / `auth.forbidden:metric:read` 等） |
| 记录来源 IP | 有 | ✅ |
| 审计概览 | 200 | `{"total":35,"success":28,"denied":7,"failed":0,"actors":5}` |
| **异步写入不丢** | `dropped=0` | `{"enqueued":35,"written":35,"dropped":0,"sync_fallback":0}` |

> **审计最重要的不是记录成功操作，而是记录被拒绝的尝试。** 只有 `denied` 记录能回答"是否有人在试探权限"。因此 401/403 一律强制留痕，即使审计模块本身出错也不影响响应返回（`try/except` 包裹）。

### 5.4 审计的不可变性

系统**不提供**修改或删除审计日志的接口。这是合规要求：审计日志一旦可改，就失去了证据价值。日志表只追加（append-only），查询权限收敛到 `admin`。

## 六、AC-P2-04 监控：Prometheus + 看板

### 6.1 指标端点

`GET /metrics` 输出标准 Prometheus 文本格式（`text/plain; version=0.0.4`），可直接被 Prometheus 抓取：

```
# HELP rag_requests_total 累计请求数
# TYPE rag_requests_total gauge
rag_requests_total 65
# HELP rag_request_duration_ms 请求耗时分位（毫秒）
# TYPE rag_request_duration_ms gauge
rag_request_duration_ms{quantile="p50"} 9.3
rag_request_duration_ms{quantile="p90"} 249.8
rag_request_duration_ms{quantile="p95"} 1528.7
rag_request_duration_ms{quantile="p99"} 1579.7
# HELP rag_auth_failures_total 认证失败次数
rag_auth_failures_total 2
rag_info{version="1.1.0-P2",env="prod"} 1
```

> 分位值跨度大是**真实模型模式**的正常表现：`/ready`、`/health` 在 10ms 内，而一次完整 RAG 问答要走 embedding + 向量检索 + DeepSeek 生成，落在 1.5s 量级。监控看 p99 才有意义，avg 会被快接口拉平。

**为什么自研而不引 `prometheus_client`**：依赖少一个是一个，且本项目只需要计数 + 分位两类能力。分位用 `deque(maxlen=1000)` 滚动窗口实现，内存恒定（不随运行时长增长），比全量直方图的桶设计更简单可控。

### 6.2 指标清单

| 类别 | 指标 |
| --- | --- |
| 流量 | `rag_requests_total`、`rag_http_requests_total{method,path,status}`、`rag_request_inflight` |
| 延迟 | `rag_request_duration_ms{quantile}`、`rag_slow_requests_total` |
| 业务 | `rag_chat_total`、`rag_chat_rejected_total`、`rag_chat_mode_total`、`rag_retrieve_total` |
| 模型 | `rag_llm_calls_total`、`rag_llm_failures_total`、`rag_llm_latency_ms`、`rag_embed_calls_total` |
| 缓存 | `rag_cache_hit_rate`、`rag_chat_cache_hit_total`、`rag_retrieve_cache_hit_total` |
| 安全 | `rag_auth_failures_total`、`rag_forbidden_total` |
| 元信息 | `rag_info{version,env}`、`rag_uptime_seconds` |

**防维度爆炸**：路径中的长 ID 会被归一化（`/documents/abc123def456` → `/documents/{id}`），否则每个文档都会生成一条独立的 label，指标基数失控。

### 6.3 看板实测

`GET /dashboard` 返回单文件 HTML 看板，无任何外部依赖（断网可用），3 秒自动刷新，支持明暗主题跟随系统。

| 区块 | 内容 |
| --- | --- |
| 核心卡片 | 运行时长、总请求、错误率、当前并发、问答总数、缓存命中率、LLM 调用与失败、认证失败、越权拦截、慢请求 |
| 延迟分布 | P50 / P90 / P95 / P99 / 平均 + 样本数 |
| 接口 TOP | 按调用次数排序的方法 + 路径 + 状态码 |

> **本轮修复**：看板原先用 `window.__HDR__` 传密钥（需手动在控制台赋值），且 `fetch` 不带任何凭证。开启鉴权后看板在生产环境**恒为 401，完全不可用**。现改为从 URL fragment 读取（`/dashboard#key=rag_xxx`）并存到 `localStorage`，fragment 不会进入服务器日志与 Referer；无密钥时在页面上给出输入框，而不是白屏报错。

### 6.4 快照与缓存管理接口

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/v1/metrics/snapshot` | `metric:read` | 结构化指标 JSON，供前端看板/外部系统 |
| `GET /api/v1/metrics/cache` | `metric:read` | L1/L2 容量、Redis 状态、分层命中率 |
| `POST /api/v1/metrics/cache/invalidate` | `kb:admin` | 人工失效（外部数据同步等场景），操作留痕 |

## 七、本轮修复的工程缺陷清单

P2 落地过程中，验收脚本暴露了 9 个此前隐藏的缺陷。这些都是"能跑但错"的类型，只有端到端断言才能发现：

| # | 缺陷 | 性质 | 影响 |
| --- | --- | --- | --- |
| 1 | 权限组写入被扩写为 `all,hr` | **安全漏洞** | 密件变全员可见 |
| 2 | 受限密钥认证后被扩写为 `all` | **安全漏洞** | 权限组隔离完全失效 |
| 3 | 上传校验无条件允许 `all` | **安全漏洞** | 受限密钥可自我扩权 |
| 4 | 文档列表"先截断后鉴权" | 正确性 | 可见文档缺失，`total` 失真 |
| 5 | `Envelope[T]` 包装导致 `data` 丢失为 `null` | 契约 | 所有命令类接口业务数据为空 |
| 6 | 看板 `fetch` 不带密钥 | 可用性 | 生产环境看板恒 401 |
| 7 | `/ready` 的 `ok` 导入被批量清理误删 | 启动阻断 | 容器启动即 `NameError` 崩溃，健康探针永不通过 |
| 8 | 会话历史接口返回注解写成 `Dict` 但实际返回 `list` | 正确性 | FastAPI 响应校验抛 `ResponseValidationError` → **500** |
| 9 | 验收脚本 multipart 分支覆盖了 `Authorization` 头 | 测试有效性 | 上传类用例全部退化为 401，**掩盖真实结果** |

### 7.0 第 7~9 项的具体成因

| 项 | 根因 | 修复 |
| --- | --- | --- |
| 7 | 为移除 `Envelope` 做批量正则替换，把 `from ... import Envelope, ok` 连带删掉了 `ok`，而 `ready()` 仍需它 | 该路径在白名单内不走中间件，改为直接返回与包装结构一致的 dict |
| 8 | P1 时未开严格响应校验，注解写错不报错；P2 后同一处直接 500 | 注解改为 `List[Dict[str, Any]]`，与存储层返回类型一致 |
| 9 | 上传分支里 `headers = {...boundary...}` 整体重新赋值，把前面注入的 Bearer 覆盖了 | 改为只更新 `headers["Content-Type"]` |

> 第 9 项最值得记录：**验收脚本自身出错时，表现和"功能缺陷"一模一样**。第一次跑 P1 回归时 8 项上传用例全红，容易误判为权限修复过头；实际是被测服务返回了正确的 401。定位方法是先用一条 `curl` 手工复现，用真实 HTTP 码对照脚本结果，才能把"脚本错"和"服务错"分开。

### 7.1 关于第 5 项：统一响应约定的正确实现

最初尝试用 `response_model=Envelope[T]` 让包装层进入 OpenAPI Schema。结果 FastAPI 会按该模型**重新序列化**返回值，而 `data` 声明为 `Dict[str, Any]` 时被过滤成 `null`——业务数据整体丢失。

**根因**：包装是"传输层关心的事"，不该由"业务层的数据模型"承担。

**最终方案**：包装由中间件在序列化之后统一完成，路由只返回业务数据并把强类型模型声明给 OpenAPI。这样既有准确 Schema，又不可能丢字段。

```python
# 中间件：业务处理之后、返回之前
response = await call_next(request)
response = await _wrap_envelope(request, response)
```

实现时踩到两个 Starlette 细节，已记录在代码注释中：

1. `JSONResponse` 继承自 `_StreamingResponse`，直接 `isinstance(resp, StreamingResponse)` 会把所有普通 JSON 响应误判为流式而跳过包装；
2. `BaseHTTPMiddleware` 下 FastAPI 的普通响应可能是 `_StreamingResponse`，`.body` 为空、内容在 `body_iterator` 里，必须异步聚合。

统一后的响应契约（成功与失败对称）：

```json
// 成功
{"code": 200, "message": "ok", "data": {...}, "trace_id": "a1b2c3d4e5f6"}
// 失败（HTTP 状态码与 code 一致）
{"code": 403, "message": "角色 viewer 缺少权限 user:admin", "data": null, "trace_id": "..."}
```

排除包装的路径：`/docs`、`/redoc`、`/openapi.json`、`/metrics`（纯文本）、`/dashboard`（HTML）。

## 九、遗留风险与后续建议

| 编号 | 风险 | 等级 | 建议 |
| --- | --- | --- | --- |
| R-P2-01 | 审计日志无自动归档，长期运行会膨胀 | 中 | P3 增加按月分区 + 冷数据导出 |
| R-P2-02 | 密钥无自动轮换 | 中 | 已支持 `expires_in_days`，建议接入企业密钥管理系统定期轮换 |
| R-P2-03 | 限流为进程内计数，多副本不共享 | 中 | 多副本部署时改用 Redis 计数器 |
| R-P2-04 | 审计异步队列满时降级同步写 | 低 | 已实现且有 `writer_stats` 可观测，压测确认阈值即可 |
| R-P2-05 | `/metrics` 公开可访问 | 低 | 如合规要求收敛，从 `AUTH_PUBLIC_PATHS` 移除并配置 Prometheus `bearer_token` |
| R-P2-06 | 无 HTTPS 终止 | 高 | 生产必须前置 Nginx/网关做 TLS，API Key 明文走 HTTP 等于泄露 |
| R-P2-07 | 无前端界面 | 中 | P3 范围，当前可通过 Swagger UI 与看板演示 |
| R-P2-08 | Redis 单点，无哨兵/集群 | 低 | 缓存层可丢，单点故障只降级为 L1-only；如要求高可用，上 Redis Sentinel |
| R-P2-09 | 单进程 uvicorn，未开多 worker | 中 | L1 是进程内缓存，多 worker 会各自维护一份，命中率下降但功能正确；扩副本时以 L2 为主 |
