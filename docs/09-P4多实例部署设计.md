# 多实例部署设计（P4 · AC-P4-07）

> 本文回答一个问题：**把单机版直接复制成 N 个副本，会在哪里坏掉，以及本项目怎么修的。**
>
> 不是"上 K8s 就自动扩容"这种空话。每一条都对应一个具体会挂的现象、一个具体的代码改动、和一个可复现的测试用例。

---

## 一、先明确：什么叫"无状态"

很多人把"无状态"理解成"服务不写本地文件"。这个理解太窄，会漏掉真正致命的东西。

对本项目来说，一个副本要能被随时杀掉、随时加一个，必须满足：

| 状态 | 存哪 | 如果留在进程内存会怎样 |
|------|------|------------------------|
| 用户身份 | JWT（客户端携带） | —— 本来就无状态 |
| JWT 签名密钥 | 环境变量 / 密钥文件 | A 签的 token 在 B 上验签失败 → 用户"刷新一次登录一次" |
| 一次性票据（jti 黑名单） | Redis | A 上注销的 token 在 B 上仍然有效 → 注销形同虚设 |
| 检索/问答缓存 | Redis + 本地 L1 | 各副本命中率被稀释，但**不影响正确性**，可接受 |
| OIDC 授权 state | Redis（本次改造） | 回调落到别的副本 → 找不到 state → 登录失败 |
| SSO 一次性票据 | Redis（本次改造） | 换票请求落到别的副本 → 找不到票据 → 被踢回登录页 |
| 告警评估状态 | Redis 锁 + 单点评估（本次改造） | 重复告警 + 连续计数被切碎 → 真故障迟迟不发 |
| 审计队列 | 后台线程 → 数据库 | 进程被 kill 时丢掉队列里未落库的记录 |
| 知识库数据 | PostgreSQL + Qdrant | —— 本来就是共享存储 |
| 文档原件 | MinIO | —— 本来就共享 |

前三条（身份、密钥、黑名单）P3 已经做完。**本文的重点是后三条**——它们是本次 P4 改造中新出现的。

## 二、本次改造的三个真实缺陷

### 2.1 OIDC 授权 state 存在进程内字典

改造前：

```python
def __init__(self) -> None:
    # 进程内保存待完成的授权。多实例部署时必须换成 Redis——
    # 否则"在 A 副本发起登录、回调落到 B 副本"会找不到 state。
    self._pending: Dict[str, _PendingAuth] = {}
```

改造前就写了这条注释，说明作者知道问题，但**代码没做**。这正是最危险的状态：文档里写了"需要注意"，实际部署时不会有人去看。

现象会是：用户点"企业登录"，IdP 认证成功，回跳到 `/api/v1/auth/sso/callback`，然后被 `302` 到 `/login?sso_error=state`。用户再点一次，可能就成功了（因为这次回调恰好落到同一个副本）。**间歇性、不可复现、看着像"IdP 不稳定"**。

改造后：

```python
_STATE_PREFIX = "rag:sso:state:"

def _save_pending(self, pending: _PendingAuth) -> None:
    r = self._redis()
    if r is not None and r.setex_raw(self._STATE_PREFIX + pending.state,
                                    STATE_TTL, payload):
        self._pending.pop(pending.state, None)      # 别在内存里留副本
        return
    self._pending[pending.state] = pending
```

两个设计要点：

**(1) 写了 Redis 就从内存删掉。** 否则同一个 state 在 Redis 和内存各有一份，两份的过期时间会漂移，`consume` 时到底读哪份取决于路径，行为不可预测。

**(2) 原子消费靠 `DEL` 的返回值，不靠 GET-then-DEL。**

```python
raw = r.get(key)
if raw is not None:
    if r.delete_keys(key) != 1:     # DEL 返回 1 = 这次是我删掉的
        return None                 # 返回 0 = 已被别人删掉（并发/重放）
```

GET 完再 DEL 是错的：两个并发回调都能读到有效 state，然后各用同一个 code 换一次 token——**一次授权产生两个会话**。这个 bug 在单实例下也能触发（用户狂点刷新），只是概率低。

### 2.2 SSO 一次性票据同样在进程内

票据是"回调"与"换票"之间的交接物，而这两个是**两个独立的 HTTP 请求**，中间隔着一次浏览器 302 + 页面加载。负载均衡完全可能把它们分到不同副本。

改造后加了 `_TICKET_PREFIX = "rag:sso:ticket:"`，逻辑与 state 同构。额外一点：票据里含 access/refresh token，属于高敏数据，所以**只放 Redis（TTL 60 秒），不进 L1 本地缓存**，避免 token 在本进程内存里多留一份。

### 2.3 告警评估会被每个副本各跑一遍

告警的"连续 N 次越线才发"依赖 `_state` 里的 `streak` 计数，而 `_state` 是进程内的。3 个副本各跑各的：

- **重复告警**：同一条真实故障，3 个副本都认为自己是"第一次越过阈值"，发 3 遍。
- **延迟告警**：streak 被切成三份，"连续 5 次"实际需要 15 个评估周期才成立。真故障来了迟迟不告警。

这是"既吵又聋"的最坏组合。

改造后加了 Redis 互斥锁：

```python
def _acquire_eval_lock(self) -> Optional[str]:
    token = secrets.token_urlsafe(16)
    # NX + EX：抢锁与设过期必须原子
    ok = layer.client.set(self._EVAL_LOCK_KEY, token,
                          nx=True, ex=max(int(settings.alert_eval_interval_sec), 5))
    return token if ok else None
```

为什么必须带 `EX`：抢到锁的副本一旦崩溃，这把锁就永远不释放，**告警从此彻底静默**——比不发告警更危险。锁的 TTL 与评估周期一致，崩溃后最多错过一轮。

释放时比对 token，避免误删别人的锁：

```python
if layer.client.get(self._EVAL_LOCK_KEY) == token:
    layer.client.delete(self._EVAL_LOCK_KEY)
```

**这一层是冗余设计。** 首选方案仍是 `ALERT_EVAL_IN_PROCESS=false` + 独立 `alert` 容器单点评估（见 compose）。但配置写错太常见了，锁兜住的正是"有人把每个 api 副本都开成 true"。

## 三、降级策略：宁可少一半功能，不能全挂

所有 Redis 迁移都保留了进程内兜底。这不是"懒得删旧代码"，而是刻意的语义：

```
Redis 可用  → 跨副本共享，多实例正常
Redis 不可用 → 各副本退回自己的内存，登录仍能用，只是跨副本的回调会失败
```

对一个登录系统来说，"部分用户登录失败"远好于"所有用户都登录不了"。Redis 挂掉时如果直接 503，就是拿一个缓存故障干掉了整个认证入口。

这一点在验收脚本里专门有 6 项用例（`fallback_no_redis`），强制把 `_redis()` 打成 `None`，验证降级路径仍能完成完整往返。

## 四、实例标识：没有它，多副本日志等于没有日志

3 个副本的日志进 Kibana 后长得**一模一样**。当出现"只有某台机器报错"的问题（本地缓存不一致、某实例连不上某个下游），你没有着手点。

所以补齐两处：

**(1) JSON 日志加 `instance` 字段**（`app_v2/core/logging.py`）：

```python
payload = {
    ...
    "service": "rag-kb",
    "instance": _instance_id(),
    "trace_id": getattr(record, "trace_id", "-"),
}
```

**(2) `/health` 与 `/ready` 暴露 `instance_id`**（`app_v2/api/routes/system.py`）：

```python
instance_id=resolve_instance_id(),
```

关键约束：**日志和 `/health` 必须用同一个值**。否则运维拿日志里的 instance 去对照 `/health` 时对不上号，排查直接卡住。所以 `resolve_instance_id()` 只是 `_instance_id()` 的公开别名，不做二次计算。

优先级：`INSTANCE_ID` 环境变量 > 容器/主机名。Compose/K8s 下 hostname 天然唯一（pod 名即实例号），留空即可；宿主机直接跑时是机器名，也够用。缓存一次，避免每条日志都调 `socket.gethostname()`。

## 五、部署拓扑

### 5.1 单机多副本（推荐给中小企业）

```
                    ┌──────────────┐
        用户 ──────► │ Nginx :80/443│  负载均衡 + TLS 终止
                    └──────┬───────┘
                 ┌─────────┼─────────┐
                 ▼         ▼         ▼
           ┌─────────┐┌─────────┐┌─────────┐
           │ api-1   ││ api-2   ││ api-3   │  ← 无状态，可随意杀/加
           │ :8000   ││ :8000   ││ :8000   │
           └────┬────┘└────┬────┘└────┬────┘
                └──────────┼──────────┘
        ┌──────────┬───────┼───────┬──────────┬──────────┐
        ▼          ▼       ▼       ▼          ▼          ▼
   ┌────────┐┌────────┐┌──────┐┌────────┐┌────────┐┌────────┐
   │ PG     ││ Qdrant ││Redis ││ MinIO  ││ ES     ││ alert  │
   │ 业务库 ││ 向量库 ││缓存/锁││ 对象存储││ 日志   ││ 单点评估│
   └────────┘└────────┘└──────┘└────────┘└────────┘└────────┘
                                          ┌────────┐
                                   celery │worker×N│ 独立扩缩
                                          └────────┘
```

**必须单点的组件**（多开会坏事）：

| 组件 | 为什么必须单点 |
|------|----------------|
| `alert` | 评估要推进 streak 状态，多开会重复告警（已加锁兜底，但仍建议单点） |
| `es` / `kibana` | 日志聚合自身状态 |
| `pg` / `qdrant` / `minio` / `redis` | 有状态存储，多开就是多套数据 |

**可以多开的**：`api`（无状态）、`celery worker`（任务队列天然可并发消费）。

### 5.2 K8s（大规模）

无状态部分直接换 Deployment + HPA；有状态部分用 StatefulSet 或直接接托管服务（RDS / ElastiCache / S3 兼容存储 / 云 ES）。

关键是无状态部分要真正无状态——见第一、二节。

## 六、编排配置的两个阻塞点

这两个问题不修，多副本**根本起不来**或**起来了会掉请求**，且报错信息都指不到真正的原因。

### 6.1 `container_name` 写死 → 无法 scale

改造前：

```yaml
api:
  container_name: rag_p4_api      # ← 致命
```

`docker compose up --scale api=3` 会直接失败，报 `container name already in use`。这个报错看起来像端口冲突（两者都涉及"已被占用"），实际是命名冲突——排查方向一开始就错了。

`worker` 同理。worker 是**天然可多副本**的组件（Celery 从 Redis 队列竞争取任务），固定名等于自断扩容能力。

改造后两个服务都不写 `container_name`，容器名自动变成 `xxx-api-1` / `-2` / `-3`。代价是运维脚本不能依赖固定名，需要用 `docker compose ps` 或 label 过滤。

### 6.2 停机窗口：Docker 默认 10 秒 vs 问答最长 120 秒

Docker 的 `docker stop` 默认给容器 10 秒，到点 **SIGKILL**。而本项目的问答会调用 LLM，单次可能跑到 120 秒。

所以 uvicorn 那侧的优雅停机配置再好也没用——外层先强杀了。必须两层都调：

```yaml
# docker-compose.yml
stop_grace_period: 150s                # Docker 这一层：给足时间

# Dockerfile
--timeout-graceful-shutdown 130        # uvicorn 这一层：等完在途请求
```

`150 > 130` 是刻意的：让 uvicorn 先自己决定什么时候退出，Docker 只作兜底。反过来的话（Docker 先杀）就浪费了优雅停机的全部意义。

这个 bug 的隐蔽之处：**日志里那条请求的 access log 是正常的**（因为它在被强杀前已经写完了），用户却收到 502。事后查日志看不出任何异常。

## 七、Nginx 配置要点

```nginx
upstream rag_api {
    # least_conn 而不是默认的轮询：本项目有长耗时的问答请求，
    # 轮询会把新请求打到正在处理 LLM 调用的副本上，加重排队。
    least_conn;
    server api-1:8000 max_fails=3 fail_timeout=15s;
    server api-2:8000 max_fails=3 fail_timeout=15s;
    server api-3:8000 max_fails=3 fail_timeout=15s;
    keepalive 32;
}

server {
    listen 443 ssl http2;

    # SSO 回调必须落在与原请求**同一个上游**吗？不需要——
    # 因为 state 已经存 Redis 了。这是本次改造带来的直接收益：
    # 有了共享 state，就可以自由用 least_conn 而不用开 sticky session。
    location / {
        proxy_pass http://rag_api;
        proxy_http_version 1.1;
        proxy_set_header Host $host;                    # IdP 校验 redirect_uri 依赖它
        proxy_set_header X-Real-IP $remote_addr;        # 全链路日志与限流要用真实 IP
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;     # 否则 Cookie 的 Secure 判断出错
        proxy_read_timeout 120s;                        # LLM 生成耗时，默认 60s 会截断
    }

    # 健康检查单独放出，不进业务路由（避免被限流/审计污染）
    location = /healthz {
        proxy_pass http://rag_api/api/v1/ready;
        access_log off;
    }
}
```

两个容易被忽略的点：

**(1) `X-Forwarded-Proto` 必须传。** 没有它，后端认为请求是 http，`_seed_state_cookie` 里 `Secure` 标志的判断会出错——最坏情况是 state Cookie 根本种不下去，表现为"点登录没反应"。

**(2) 不开 sticky session 是改造后的能力。** 如果 state 还在进程内，就必须配 `ip_hash` 或 cookie sticky，而 sticky 一旦失效（客户端换 IP、负载不均）登录就随机失败。现在不需要了。

## 八、部署检查清单

上线前逐项确认。**每一项都对应一个曾经真实发生的故障**：

### 7.1 配置

- [ ] `JWT_SECRET` 所有副本**完全一致**（不一致 → 刷新即掉登录）
- [ ] `JWT_SECRET` 不是代码默认值，且不随镜像分发
- [ ] `REDIS_URL` 所有副本指向**同一个** Redis
- [ ] `MINIO_*` / `META_BACKEND=postgres` / `VECTOR_BACKEND=qdrant` 指向共享存储
- [ ] `ALERT_EVAL_IN_PROCESS=false` 在**所有 api 副本**上（只有 alert 容器评估）
- [ ] `OIDC_REDIRECT_URI` 是**外部可访问**的完整地址，与 IdP 侧登记值逐字符一致
- [ ] `OIDC_TENANT_CLAIM` 已配置（否则所有 SSO 用户落到默认租户，租户隔离形同虚设）
- [ ] `INSTANCE_ID` 留空（由 hostname 自动生成）或显式设置为唯一值

### 7.2 验证（逐条 curl）

```bash
# 1. 每个副本都活着，且 instance_id 各不相同
for p in 8001 8002 8003; do
  curl -s http://127.0.0.1:$p/api/v1/health | jq -r '.data.instance_id'
done
# 期望：输出 3 个不同的值

# 2. A 副本登录拿到的 token，在 B 副本可用（验证 JWT secret 共享）
TOKEN=$(curl -s -X POST http://127.0.0.1:8001/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"***"}' | jq -r '.data.access_token')
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8002/api/v1/auth/me \
  -H "Authorization: Bearer $TOKEN"
# 期望：200

# 3. Redis 里能看到 state 前缀（证明真的走了 Redis 而非内存降级）
redis-cli --scan --pattern 'rag:sso:state:*' | head

# 4. 日志里 instance 字段有值
docker logs api-1 2>&1 | tail -1 | jq -r '.instance'
```

### 7.3 滚动发布

```
1. 先扩一个新副本（副本数 N → N+1），等 /api/v1/ready 返回 200
2. 从负载均衡摘掉一个老副本（Nginx: 标记 down；K8s: 触发 rollingUpdate）
3. 等该副本上**在途请求**结束（graceful shutdown，见下）
4. 杀进程，重复直到全部替换
```

**graceful shutdown 不能省。** uvicorn 默认收到 SIGTERM 会等待在途请求，但如果把 `--timeout-graceful-shutdown` 设得太小，正在跑 LLM 生成的请求会被腰斩，用户看到 502。本项目问答最长可能 120 秒，建议至少 130。

### 7.4 回滚

镜像 tag 不变、只改配置的话，回滚就是重启。真正的风险在**数据库 schema**：P4 给 `audit_logs` 加了 `tenant_id` 列。回滚到 P3 版本时代码不写这一列，列上有默认值所以不会报错——但**回滚期间产生的审计记录会全部堆在 `default` 租户**。如果需要回滚，应同时接受"这段时间的审计租户信息丢失"，或先停写审计。

### 8.1 为什么 [2] 用"两个 OIDCService 实例"而不是两个 HTTP 请求

OIDC 的 state 是服务端私有的，浏览器拿不到明文——**这正是它安全的原因**。所以没法通过 HTTP 让"副本 A 创建 state，副本 B 消费"这条路径可观测。

替代方案是用两个独立的 `OIDCService` 实例模拟两个副本的进程状态。它们**完全不共享内存**（脚本先断言 `node_a._pending is not node_b._pending`），唯一共同点是 Redis。B 能消费到 A 写的 state，就证明状态确实落在 Redis。

### 8.2 脚本自身踩过的坑（值得记录）

第一版脚本全绿之前，有过一轮"假绿"和一轮"假红"，都很有代表性：

**假绿**：`REDIS_URL` 在 `main()` 里才设置，而模块在文件顶部就 import 了。settings 在 import 期读环境变量，之后再改 `os.environ` **不会生效**。结果是代码明明写了 Redis，测试却全程走内存降级——所有断言都通过，但验证的是错的东西。

修复：把 `os.environ["REDIS_URL"] = ...` 提到模块级，在任何 `app_v2` 导入之前。

**假红**：登录接口写成了 `/auth/token`，实际是 `/auth/login`，422 被误判成"多实例有问题"。

**假红**：`/health` 写成了 `http://127.0.0.1:8021/health`，实际是 `/api/v1/health`。

后两个是纯粹的手误，但它们说明一件事：**验收脚本报错时，先怀疑脚本，再怀疑代码。** 否则会去"修"一个不存在的 bug，反而把好代码改坏。

### 8.3 真实双容器实测（不只是脚本）

脚本验证的是逻辑，但"能不能真的跑起来两个副本"必须用真实容器证明。用重建的 `rag-kb-p4-api` 镜像起两个容器，接入**同一套** PostgreSQL / Qdrant / Redis：

```
replica-1 :8032  →  instance_id = replica-1
replica-2 :8033  →  instance_id = replica-2      ← 同镜像、同存储、标识可区分
```

**跨副本 JWT（secret 共享）**

```
A 副本签发 token 长度: 381
在 B 副本使用 → HTTP 200
```

**跨副本注销（黑名单共享）** —— 这条最容易漏，因为单实例测试永远正常

```
注销前 B 副本校验 → HTTP 200
在 A 副本注销     → HTTP 200
注销后 B 副本校验 → HTTP 401      ← A 上注销，B 立即失效
注销后 A 副本校验 → HTTP 401
```

如果黑名单只存进程内存，就会变成"在 A 注销了，切到 B 还能用"——用户以为已经登出，实际会话仍然有效。

**优雅停机**

在持续打问答请求的同时执行 `docker stop`，观察停机窗口：

```
... POST /api/v1/chat -> 200 (20ms)
... POST /api/v1/chat -> 200 (20ms)
... POST /api/v1/chat -> 200 (20ms)
... POST /api/v1/chat -> 200 (20ms)
INFO:     Shutting down
INFO:     Waiting for application shutdown.
... 服务关闭
INFO:     Application shutdown complete.
```

`Shutting down` 之前的在途请求全部完成并正常写日志，没有一条被腰斩。对比 Docker 默认的 10 秒强杀：`Application shutdown complete` 根本不会出现，日志会断在请求中途。

## 十、已知限制

诚实列出还没做的部分：

1. **审计队列在进程被 kill 时会丢未落库的记录。** 当前是后台线程 + 队列（`enqueue` / `flush`）。优雅停机（SIGTERM）会 flush，但 `kill -9` 或 OOM 不会。彻底解决要把审计写入也走 Celery/消息队列，属于下一阶段。

2. **告警锁的释放不是原子的。** `GET` 比对 + `DELETE` 之间存在窗口，极端情况下可能误删别的副本刚抢到的锁。后果仅是"某一轮可能两个副本同时评估"，可接受。换成 Lua 脚本可完全解决，但会引入对 `EVAL` 的依赖。

3. **本地 L1 缓存不跨副本失效。** 文档更新时 `invalidate_knowledge()` 只清本副本的 L1 和共享的 Redis L2。其他副本的 L1 会保留最多 60 秒旧值（L1 TTL 上限）。表现为"改了文档，某些用户的回答 1 分钟内还是旧的"。对知识库场景可接受——这不是转账余额。

4. **没有做跨副本的限流精确同步。** 限流计数走 Redis（`incr_with_ttl`），是**全局**的，多副本下总限流额度不变——这一点是对的。但如果 Redis 降级，每个副本各自计数，实际额度变成 N 倍。降级期间限流精度下降是已知取舍。
