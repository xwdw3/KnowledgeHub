## P1：核心链路验证（已完成）

### 为什么先做这个

RAG 项目最大的失败风险不是"架构不够先进"，而是**跑起来发现检索不准、答案还是编**。这个风险必须第一周就验证，不能等到系统建完。

所以 P1 刻意**砍掉了所有非核心的东西**：

| 砍掉 | 原因 |
| --- | --- |
| Qdrant / PostgreSQL | 会把验证重点从"效果"转移到"部署" |
| 用户权限 | 单机原型无多用户场景 |
| 缓存 | 优化项，不影响链路成立 |
| Agent 工具调用 | 增加不确定性，先固定管道更容易定位问题 |
| 流式输出 | 体验项，P2 再做 |

### 交付物

```
p1_prototype/
├── run.py                    启动入口
├── requirements.txt          最小依赖（8 个包）
├── .env.example              配置模板
├── app/
│   ├── config.py             统一配置（复用根目录 .env 的模型密钥）
│   ├── loader.py             文档解析 txt/md/pdf/docx + 清洗（含表格）
│   ├── splitter.py           段落优先递归切片 + jieba 中文分词
│   ├── embedder.py           BGE-M3 向量化 + 离线哈希向量兜底
│   ├── store.py              本地 numpy 双索引（向量 + BM25），单文件落盘
│   ├── retriever.py          双路召回 → RRF 真实融合 → 相关度评估
│   ├── rag.py                上下文拼装 → 生成 → 引用 → 拒答
│   ├── ingest.py             入库编排（幂等覆盖、批量导入、删除一致性）
│   └── main.py               FastAPI + 单页演示界面
├── data/
│   ├── docs/                 演示语料（3 份真实制度文档）
│   └── index/                index.npz + meta.json
├── scripts/verify.py         14 项端到端自动验收
└── docs/演示脚本.md           8~10 分钟演示讲解稿
```

### 关键技术点

1. **RRF 真正双路融合**：分别对向量排名和 BM25 排名计算 `1/(k+rank)` 再相加。旧实现只对单路结果计分，等于没融合。
2. **相关度拒答**：用"向量余弦 + BM25 绝对分 + 查询词覆盖率"三项加权，覆盖不足时压分。实测库内 ≥0.61、库外 ≤0.18，阈值 0.25 有充足余量。
3. **切片粒度**：段落优先，超长段回退到句子级，短段贪心合并。实测 188~495 字，主题独立。
4. **离线兜底**：无模型密钥时自动切本地哈希向量 + 抽取式作答，保证演示永不失败。

### P1 已知局限（刻意保留，P2 解决）

- 索引单文件落盘，不支持并发写，适合单机原型
- 会话不持久，刷新即丢失
- 无权限隔离，所有文档对所有人可见
- 无引用高亮、无答案反馈

## P2：工程化（✅ 已完成——实际执行以 06-P2阶段验收文档.md 为准）

### 目标

把原型变成能给真实员工用的系统，核心补齐**安全、性能、可运营**三块。

### 任务清单

| 优先级 | 任务 | 说明 |
| --- | --- | --- |
| P0 | 索引层迁移 Qdrant | 保持 `retriever` 接口不变，只换实现；payload 带 `perm` |
| P0 | 元数据迁移 PostgreSQL | 文档表补上传人、时间、权限组、状态 |
| P0 | 用户身份接入（SSO） | 会话与用户绑定，权限组自动带入检索 |
| P1 | 问题级 + 向量级缓存 | 热点问题 <200ms，文档变更自动失效 |
| P1 | 流式输出 | 首字 <2s，改善等待体验 |
| P1 | 文档管理页 | 列表、搜索、权限设置、批量删除 |
| P1 | 指标看板 | 问答量、无答案率、耗时、热门问题、知识盲区 |
| P2 | 引用高亮与答案反馈 | 命中词高亮，👍/👎 收集质量信号 |

### 验收门槛

- 50 条标准问题集召回命中率 ≥90%
- 低权限账号检索高密文档返回空，无任何片段泄露
- 缓存命中 P95 <200ms，完整问答 P95 <5s

## 迭代节奏建议

| 周期 | 内容 |
| --- | --- |
| 第 1 周 | P1 完成（已验证） |
| 第 2–3 周 | P2 索引与元数据迁移 + 身份接入 |
| 第 4 周 | P2 缓存、流式输出、文档管理页 |
| 第 5 周 | P2 指标看板 + 评测集建设 + 上线试运行（选 1 个部门） |
| 第 6 周起 | P3 按业务反馈排期 |

**关键原则**：P2 上线前必须建立**评测集**（50~100 条真实问题 + 标准答案），否则后续所有优化都无法判断是否真的变好了。
