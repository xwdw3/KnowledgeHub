## 二、标准 1：所有接口必须携带 JWT Token

### 2.1 设计：从"双通道"收敛到"单一票据"

P2 的设计是 JWT 与 API Key **并存**。但验收标准要求"所有接口必须携带 JWT"，两者不能同时成立，因此改为：

```
API Key ──POST /auth/token──► JWT（access + refresh）──► 业务接口
账号密码 ──POST /auth/login──► JWT ──────────────────► 业务接口
                                    ▲
                            业务接口只认这一个入口
```

API Key 仍然是**唯一的长效凭据**，但它的作用被降级为"换票凭证"——就像一个只能开发票、不能直接开门的窗口。

**为什么必须这样改**：长期密钥一旦泄露就是永久后门。让密钥只能换"短期票据"，票据有有效期、可注销（jti 黑名单）、权限变更即时生效，风险窗口从"永久"压缩到"最长 30 分钟"。

### 2.2 实测证据

| 检查项 | 结果 | 实测输出 |
| --- | --- | --- |
| 18 个业务端点无凭证 | 全部 401 | `18/18` |
| 5 种畸形 Token | 全部拒绝 | `全部拒绝` |
| 有效 API Key 直连业务接口 | **拒绝** | `401 当前为 JWT 强制模式（AUTH_MODE=jwt）：API Key 不能直接访问业务接口，请先 POST /api/v1/auth/token 用 API Key 换取 JWT` |
| 拒绝时给出换票指引 | 有 | 同上（错误信息本身即引导） |
| `/health`、`/auth/methods` | 免凭证可用 | `200` / `mode=jwt` |
| `/metrics` 无令牌 | 401 | `status=401` |
| `/metrics` 带抓取令牌 | 200 | `status=200` |
| 注销后同一 Token | 立即 401 | `status=401`（jti 黑名单） |

### 2.3 两个必须解释的例外

**(1) `/metrics` 为什么不用 JWT？**

Prometheus 只支持**静态 header**，无法执行"登录 → 拿 token → 到期刷新"这套流程。因此 `/metrics` 使用**独立抓取令牌**（`METRICS_TOKEN`），并用 `hmac.compare_digest` 做常量时间比较。

这不是放松要求——`/metrics` 会暴露接口路径、状态码分布、依赖拓扑，等于系统全貌，**绝不能裸奔**。用独立令牌是"在 Prometheus 的能力边界内，做到同样强度的保护"。

**(2) 免认证路径为什么存在？**

登录、健康检查、接口文档如果也要求 JWT，会形成逻辑闭环（要登录先得登录）。因此精确白名单：

```
/auth/login, /auth/refresh, /auth/methods, /auth/token,
/health, /ready, /docs, /redoc, /openapi.json
```

白名单是**精确匹配**而非前缀匹配——`/auth/users` 不会被 `/auth/` 前缀放行。

## 三、标准 2：不同角色只能查看授权范围内内容

### 3.1 核心不变量：空间与密级正交

这是整个权限体系里**最容易写错、且写错了最危险**的地方。系统里有两个名字都叫 "hr" 的概念：

| 概念 | 字段 | 回答的问题 | 取值示例 |
| --- | --- | --- | --- |
| **空间**（spaces） | `users.spaces` | 能进哪些**业务域** | `default` / `hr_zone` / `rd_zone` |
| **密级**（perm_groups） | `users.perm_groups` | 在同一域内能看哪些**密级片段** | `all` / `hr` / `finance` |

二者**恰好常取同名值**，但语义完全不同，**绝不能互相赋值**：

- 若把密级当空间：P2 存量密钥（`perm_group=hr`）会被判为"无权访问 default 空间"，升级后所有上传/检索 403；
- 若把空间当密级：跨空间内容互相可见，隔离直接失效。

上一轮就真实踩中过第一条（详见第七章缺陷 1），所以这次在 `Principal` 的 docstring 里把这条写成了硬约束。

### 3.2 更细的一层：读范围 ≠ 写范围

这一轮新发现并修复的缺陷（第七章缺陷 3），本质是**同一个字段被两个方向的默认值共用**：

| 方向 | 是否自动补 `all` | 为什么 |
| --- | --- | --- |
| **读取** | ✅ 补 | 公共文档本来就该人人可读，不补会导致谁都看不到公开文档 |
| **写入** | ❌ 不补 | 补了就等于每个受限用户都"拥有 all"，`editor(hr)` 能把 hr 密件标成 `all` **公开给全员** |

因此 `Principal` 拆成两个字段：`perm_groups`（读取范围，含自动补的 all）与 `granted_perm_groups`（写入范围，只反映显式授权）。

### 3.3 实测证据

| 检查项 | 结果 | 实测输出 |
| --- | --- | --- |
| 普通用户提问机密问题 | 拒答 | `rejected=True sources=1`（仅公共文档） |
| 响应不含 hr 密级片段 | 通过 | `perm_groups=[]` |
| 普通用户可读公共文档 | 通过 | `sources=1 rejected=False` |
| 文档列表不含机密文件 | 通过 | 共 1 条：`['acc_public_*.md']` |
| default 空间用户看不到 accptest | 通过 | 可见空间 `['default']` |
| 越权指定 space_id | **403** | `无权访问知识库空间 accptest，当前可访问 ['default']` |
| 显式授予 hr 密级后 | 可召回 | `perm_groups=['all','hr'] sources=3` |
| **未授予 hr 的 kb_admin** | **读不到** | `rejected=True`（密级不由角色白送） |
| 普通用户调管理接口 | 403 | `/auth/users`、`/audit/logs`、`/metrics/snapshot` 均 403 |
| 普通用户上传 | 403 | `角色 user 缺少权限 kb:write` |
| **管理员预热缓存后，普通用户仍读不到** | 通过 | `rejected=True`（缓存 key 含权限维度） |

### 3.4 三条设计原则

1. **权限来自显式数据授权，不来自代码里的隐式规则。** `_derive_perm_groups` 刻意不做"角色是 admin 就自动给全密级"的推导——隐式规则一旦写错，就是"所有人都能看薪资表"这种事故。管理员需要全密级时，把 `perm_groups` 显式设为 `*`。
2. **越权返回 403 而不是空结果。** 空结果会让调用方误以为"真的没有数据"，从而反复尝试。
3. **缓存不能绕过权限。** 缓存 key 里包含权限维度，否则"管理员问过一次"就等于把答案缓存给了所有人。

## 四、标准 3：相同问题命中缓存，减少 LLM 调用

### 4.1 实测证据

取证方法**不依赖服务端自述的 `cached` 字段**——直接读进程内 `rag_llm_calls_total` 计数器的差值：

| 检查项 | 结果 | 实测输出 |
| --- | --- | --- |
| 首次未命中 | 通过 | `cached=False` |
| 首次真实产生 LLM 调用 | 通过 | `llm_calls 45 → 47`（+2，含向量化与生成） |
| 5 次重复提问 | 全部命中 | `cached` 均为 `True` |
| **重复提问未新增 LLM 调用** | **通过** | `llm_calls 47 → 47`（**零增长**） |
| 缓存命中计数 | +5 | `cache_hit 0 → 5` |
| 命中显著快于首次 | 通过 | `0.0ms < 2866ms` |
| 多轮对话上下文可读回 | 通过 | `turns=4` |
| 上下文确实缓存了历史轮次 | 通过 | `200/200` |

**这是最硬的一条证据**：如果只是"返回了 cached 标记但实际仍在调 LLM"，计数器不可能停在 47 不动。

### 4.2 两级缓存

```
请求 ──► L1 本地 LRU（进程内，微秒级）
           │ miss
           ▼
         L2 Redis（跨实例共享）
           │ miss
           ▼
         真实链路（检索 + Rerank + LLM）
```

- **L1** 挡住单实例内的重复请求，省掉网络往返；
- **L2** 让多实例共享结果，扩容时缓存命中率不会掉；
- Redis 不可用时**自动降级**为纯本地缓存，服务不中断。

## 七、标准 6 与 7：混合检索 + Rerank，准确率提升

### 7.1 混合检索的四项证据

单条检索结果同时携带四路分数，可逐层核对：

```
['bm25_rank', 'bm25_score', 'chunk_id', 'file_name',
 'rerank_score', 'rrf_score', 'seq', 'space_id', 'text',
 'vec_rank', 'vec_score']
```

```
向量检索（语义）──┐
                  ├─► RRF 融合（k=60）──► Rerank（LLM 打分）──► Top-K
BM25（词面）  ────┘
```

**为什么需要两路**：向量检索擅长"意思相近"（"住宿标准" ↔ "房价上限"），但对精确词（文号、金额、专有名词）不敏感；BM25 正好相反。RRF 按**名次**融合而非分数——向量分是余弦相似度、BM25 分是无界实数，两者量纲不同，直接加权需要调参且不稳定。

**重排实测**：`by_mode={'llm': 31}`，降级 `0/31 (0%)`。

### 7.2 准确率对照实验（标准 7）

**实验设计**：这一步是关键——第一版实验三档全部 100%，因为语料里每篇文档主题截然不同，任何检索都能命中。重写为**"正确文档 + 高相似干扰文档"配对**：

| 正确文档 | 干扰文档 | 干扰为何有迷惑性 |
| --- | --- | --- |
| 境内差旅 | 境外差旅 | 都含"差旅/住宿/报销" |
| 年假 | 调休 | 都是"假期/天数" |
| 报销 | 付款 | 都含"审批/提交/时限" |
| 薪酬 | 预算 | 都含"调薪/幅度/审批" |
| 信息安全 | VPN | 都含"密码/更换/周期" |

题库分三层：L1 词面重合、L2 干扰配对、L3 口语化（"干了三年的话假期能有几天"）。

**结果**：

| 档位 | Hit@1 | Hit@3 | MRR | 干扰胜出 |
| --- | --- | --- | --- | --- |
| `off`（不重排） | 90% | 100% | 0.950 | 1/10 |
| `heuristic`（本地启发式） | 90% | 100% | 0.950 | 1/10 |
| **`llm`（模型打分）** | **100%** | 100% | **1.000** | **0/10** |

**唯一失败题**：`我出差住酒店的钱能报多少` —— 在 off/heuristic 两档，境外差旅文档排第 1；llm 档修正为境内差旅第 1。

**为什么 heuristic 档也救不回来**：启发式只算"查询词在文档里的覆盖度"，而 `酒店`、`报多少` 与境外文档的词面重合度同样高，它**没有能力判断"境内/境外"这个决定性差异**。这正是 LLM 重排的价值所在——它读懂的是语义约束，不是词频。

**提升幅度表述**：Hit@1 从 90% 到 100%（错误率从 1/10 降到 0），MRR 从 0.950 到 1.000。在 10 题小样本上，绝对提升 +10pp；从错误率看是**减少 100% 的错误召回**。

## 八、本轮修复的 4 个真实缺陷

这一轮验收不是为了"跑绿"，而是把 7 条标准当作探针去压系统。**压出了 4 个真实缺陷，其中 2 个是安全性质。**

### 缺陷 1：`/auth/token` 把密级当成了空间（升级即破坏）

**现象**：`editor(hr)` 换票后上传文档报 403 —— `无权在该空间投放文档：default，当前可访问 ['hr']`。

**根因**：换票时写了 `"spaces": ",".join(principal.perm_groups)`，把 API Key 的 `perm_group`（密级）填进了 `spaces`（空间）。

**为什么危险**：这正是第三章强调的"两套范围概念不能互相赋值"的反面教材。受影响的不只是测试账号——**所有 P2 存量密钥在升级后都无法上传文档**，属于"一升级就全挂"的破坏性变更。

**修复**：`spaces` 落默认空间（与 P2 行为一致），`perm_group` 映射到 `pg`（密级）。

### 缺陷 2：`_llm_rerank` 注释与实现不符（并列退化）

**现象**：三档 Rerank 的 Hit@1 完全一样（都是 90%），看起来"重排没生效"。

**诊断**：dump 出 `eval_travel_city.md` 与 `eval_travel_abroad.md`，两者的 `rerank_score` **都是 1.0000**。

**根因**：LLM 打分是 0-10 的整数，候选稍多就必然并列。并列时若只按 `rerank_score` 排序，相对顺序完全取决于 `sorted` 的稳定性 + 输入顺序，**等价于没重排**。

更值得注意的是：代码注释里明明写着"原始 RRF 名次做微弱保留，防止模型打分全相同时顺序随机"，**但代码根本没实现**——注释与实现不符，是最难发现的那类缺陷，因为读代码的人会相信注释。

**修复**：加 `_orig_rank` 二级排序键（先比 `rerank_score`，再比 RRF 名次）。

**效果**：llm 档 Hit@1 **90% → 100%**，MRR **0.950 → 1.000**，干扰胜出 **1/10 → 0/10**。

### 缺陷 3：写入范围继承了读取范围的 `all`（越权漏洞）

**现象**：修完缺陷 1 后，`editor(hr)` 突然能**把文档投放到 `all`**（HTTP 200）——而在修复前这是被正确拒绝的（403）。

**根因**：`_check_perm_group` 用 `principal.perm_groups` 判断写入权限，而 `_derive_perm_groups` 会**无条件追加 `all`**（为了让人人能读公共文档）。于是每个受限凭据都"拥有 all"，`editor(hr)` 就能把 hr 密件标成 `all` 公开给全员。

**为什么这是最危险的一个**：它不是"拒绝了不该拒绝的"，而是"放行了不该放行的"。前者会报错、会被发现；后者**静默生效**——密件被标成 all 之后，所有人都能搜到，而没有任何报错。

**修复**：`Principal` 拆出 `granted_perm_groups`（写入范围，不补 all），读取继续用 `perm_groups`（补 all）。两个方向的默认值必须是反的。

**修复后**：`403 无权将文档归入权限组 all，当前凭据仅限 ['hr']`，同时 `A19 editor(hr) 上传 hr 密级文档成功 200` 保持正常。

### 缺陷 4：吊销密钥无法作废已签发的票据

**现象**：`E4 被吊销密钥立即失效` 测试返回 200（应 401）。

**根因**：吊销密钥只关掉了"换票入口"，已经换出去的 JWT 仍然能用满整个 TTL（30 分钟）。

**为什么这在真实场景里是问题**：员工离职、密钥泄露这类场景，处置动作就是"吊销密钥"。如果已发出的票据还能用 30 分钟，那 30 分钟足够把整库文档导出。

**修复**：换票时把来源密钥写进 JWT payload（`sk` 字段），`principal_from_jwt` 每次校验都回查该密钥状态。吊销密钥 → 用它换出的所有票据同时作废。

## 十、遗留事项与建议

### 10.1 已知限制（不影响本阶段验收）

| 项 | 现状 | 建议 |
| --- | --- | --- |
| 准确率实验样本量 | 10 题配对语料 | 上线前用真实业务问题扩到 50~100 题，按业务域分层 |
| Rerank 延迟 | LLM 打分比 heuristic 慢 | 已设 12s 超时 + 自动降级；高并发场景可考虑批量打分或小模型 |
| Grafana 匿名查看 | 看板页面可匿名打开（数据需令牌） | 生产环境建议关闭，走统一 SSO |
| 密钥轮换 | 支持吊销，但无自动轮换 | 建议加"到期提醒"与"双密钥并行过渡" |

### 10.2 三条给运维的建议

1. **先看第五组面板。** 看板从"服务健康"到"答案质量"分组，日常巡检按 ③ 错误率 → ④ 依赖负载 → ⑤ 检索质量的顺序看，能在用户投诉前发现问题。
2. **关注 `rag_rerank_fallback_total`。** 这个指标上升意味着 LLM 重排在降级，答案质量会静默下滑——它不报错，只是慢慢变差。
3. **`/metrics` 令牌要按敏感凭据管理。** 它能反映系统全貌，泄露的危害等同于泄露架构图。
