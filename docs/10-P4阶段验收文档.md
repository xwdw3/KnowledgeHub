## 二、验收模块逐条说明

### 2.1 异步任务队列（AC-P4-01）

**做了什么**：Celery + Redis。文档上传后的解析、切片、向量化从"同步阻塞接口"改为"入队 + 轮询任务状态"。

**为什么必须做**：一份 200 页 PDF 的解析 + 向量化要几十秒。同步接口下：
- 用户点击上传后页面卡住，以为没反应又点一次 → 重复入库；
- Nginx / 网关默认 60 秒超时 → 大文档必然 504，但后端其实还在跑，产生"幽灵文档"。

改成异步后接口立即返回 `task_id`，前端可展示进度。

**验收**（18/18）：

```
PASS  任务结果含 chunk_count   chunks=1
PASS  文档已落库且归属 acme
PASS  文档不会被写到默认租户
```

最后两条是重点：**异步任务最容易丢租户上下文**。任务在 worker 里执行，而 worker 没有 HTTP 请求上下文，如果直接把 `tenant_id` 从入参丢弃、在任务里"取当前租户"，就会落到默认租户——表现为"上传成功但文档跑到别的公司去了"。所以租户 ID 必须作为任务参数显式传递。

### 2.2 MinIO 对象存储（AC-P4-02）

**做了什么**：文档原件存 MinIO，业务库只存 `object_key`。

**降级设计**：MinIO 关闭时上传仍成功，`object_key` 为空，下载返回 404 并说明原因。

```
PASS  上传时 object_key 为空但文档可用   已在 MinIO 关闭状态下完成上传
PASS  无原件时下载链接返回 404 并说明原因   HTTP 404
```

这个降级是有意的：MinIO 挂掉不应该让整个知识库无法使用——切片已经入库，问答仍然可用，只是不能下载原件。**功能降级优于服务不可用**。

### 2.3 ELK 日志集群（AC-P4-03）

**做了什么**：Filebeat 无需额外安装——应用直接写 JSON 到共享卷，Logstash 采集 → ES → Kibana。

**关键约束**：ES 在小内存机器上是"内存黑洞"。本项目锁定：
- ES 堆 `-Xmx512m` + `-Xms512m`（堆不锁会被 JDK 按物理内存的 1/4 申请）
- Logstash 堆 256MB
- 单节点、关闭副本（`number_of_replicas: 0`），否则单节点集群会一直 yellow 并拒绝写入

**多副本要点**：日志必须带 `instance` 字段，否则 3 个副本的日志在 Kibana 里无法区分（详见部署设计文档第四章）。

### 2.4 告警通知（AC-P4-04）

**做了什么**：规则化告警（阈值 + 连续 N 次越线）+ 多通道路由（Webhook / 邮件 / 仅入库）。

**"连续 N 次"为什么必要**：单点越线就告警，会被正常的流量毛刺淹没。运维一旦开始忽略告警，告警系统就等于不存在。

**验收**（39/39）中值得单说的三条：

```
PASS  对端不可达时评估仍返回（不抛异常）
PASS  失败渠道记入 db-only 而不是丢弃   ['db-only']
PASS  沉默期内不重复通知
```

第一条：Webhook 对端挂了不能把评估线程带崩，否则一次网络故障就让整个告警系统停摆。
第二条：投递失败的告警必须落库。否则"发过的告警因为发送失败而彻底消失"，事后查不到。
第三条：告警风暴比不告警更糟。

**多副本问题及修复**：见 2.7 与部署设计 2.3 节（Redis 互斥锁）。

### 2.5 前端系统（AC-P4-05）

**技术选型**：原生 HTML/CSS/JS 单页，零构建，FastAPI 静态托管。

**为什么不用 React/Vue**：本项目前端的核心诉求是"企业内部知识库"，不是高交互的 C 端产品。引入构建链意味着：
- 交付物从"一个镜像"变成"镜像 + node_modules + 构建步骤 + 构建缓存"；
- 私有化交付时客户环境可能没有 node，需要额外维护构建产物；
- 一个 XSS 漏洞的修复要重新走一遍 CI。

零构建的代价是代码组织靠纪律（6 个 CSS 分层、5 个 JS 模块），但对这个规模是划算的。

**三个页面**：

| 页面 | 文件 | 行数 | 核心内容 |
|------|------|------|----------|
| 登录 | `login.html` + `login.css` + `login.js` | 175+357+224 | 账号密码 + SSO 按钮 + 错误短码映射 |
| 聊天 | `app.html` + `app.css` + `app.js` + `markdown.js` | 230+681+757+190 | 会话列表、流式回答、来源溯源、引用跳转 |
| 管理后台 | `admin.html` + `admin.css` + `admin.js` | —+459+1019 | 文档/空间/用户/租户/审计/告警/任务 |

**验收实测**：端到端 17/17 中覆盖了"页面免认证可访问、数据经 API 鉴权"这条关键路径。

前端曾出现一个真实缺陷：`/login` 页面本身返回 401。原因是中间件把 HTML 页面当业务接口要求 JWT——**登录页自己需要登录，形成死循环**。修复方式是在 `is_public()` 里显式放行前端页面与 `/static/`。

这里的设计原则：**页面免认证，数据全鉴权**。页面本身不含任何数据，所有数据都来自带 token 的 API 调用，所以放行页面不产生泄露风险。

### 2.6 多租户隔离（AC-P4-06）

**三层正交隔离**：

```
tenant_id（哪家公司） → space_id（哪个业务域） → perm_group（什么密级）
```

顺序不可颠倒，三层都必须下推到检索时（向量库 filter + SQL where），缺一层等于没隔离。

**验收**（19/19）关键项：

```
PASS  合法 ID 规范化通过
PASS  文档配额超限被拦下   租户 acme 文档数已达上限（1/1）
PASS  租户由 IdP claim 判定 = acme
```

**本阶段修复的真实缺陷**：

1. **审计表未写 `tenant_id`**。`log_audit` 的 INSERT 少了一列，所有记录都堆在 `DEFAULT 'default'` 上。后果：B 租户的管理员在审计页能看见 A 租户的全部操作。修复：SQL 补列 + `record()` 从上下文自动取租户。

2. **claims 里租户非法时静默降级**。原实现在租户 ID 不合法时 `except` 掉并退回默认租户。这是**静默串户**：A 公司的人被丢进 default 租户，登录成功然后看到别人的内容。修复：claims 路径不捕获异常（直接 422），只有用户输入的 hint 允许降级。

3. **缺租户管理 API**。多租户服务实现了，但运维开新公司要连数据库执行 SQL——"隔离"成了只有开发者能用的能力。修复：新增 `POST/GET/GET{id}/PATCH{id}` 四个接口，全部 `PERM_KB_ADMIN` 且记审计。

### 2.7 多实例部署（AC-P4-07）

**详见** `docs/09-P4多实例部署设计.md`。此处只列结论。

**三个真实缺陷**（都是"单实例永远测不出来"的类型）：

| 缺陷 | 现象 | 修复 |
|------|------|------|
| OIDC state 存进程内字典 | 登录随机失败（回调落到别的副本），重试又好了 | 迁 Redis，原子 `DEL` 判重 |
| SSO 票据存进程内字典 | 换票时提示票据无效，被踢回登录页 | 迁 Redis，同上 |
| 告警评估每副本各跑一遍 | 重复告警 + 连续计数被切碎导致延迟告警 | Redis 互斥锁 + 单点 alert 容器 |

**编排层两个阻塞点**：

- `container_name` 写死 → `--scale` 直接失败，报错像端口冲突实为命名冲突；
- Docker 默认 10 秒强杀 vs 问答最长 120 秒 → 在途请求被腰斩，用户 502 但日志正常。

**验收**（34/34 + 真实双容器实测）：

```
instance_id: replica-1 / replica-2                    ← 副本可区分
A 副本签发 token → B 副本使用 → HTTP 200               ← JWT secret 共享
在 A 副本注销 → B 副本立即 401                         ← 黑名单共享
Shutting down 前 4 个在途请求全部 200 完成              ← 优雅停机生效
```

第三条尤其关键：如果黑名单只存内存，会变成"在 A 注销了，切到 B 还能用"——用户以为登出，实际会话仍有效。

### 2.8 企业 SSO 单点登录（AC-P4-08）

**协议**：OIDC Authorization Code Flow + PKCE。

**为什么不用 SAML**：企业身份源（Keycloak / Azure AD / 飞书 / Authing）现在都提供 OIDC；SAML 的 XML 签名校验实现复杂且易错（XML 规范化攻击、签名包裹攻击）。OIDC 是 JSON + JWT，可直接复用已有的 JWT 能力。

**五个安全点，每个都有对应测试**：

| 安全点 | 防的是什么 | 实现 |
|--------|-----------|------|
| state 一次性 | 登录 CSRF | 服务端存储 + `DEL` 原子判重 |
| state 与浏览器双绑 | 攻击者用自己的 code 诱导受害者 | HttpOnly Cookie + `compare_digest` |
| nonce 校验 | ID Token 重放 | 授权时下发，回调时比对 |
| code 服务端换取 | client_secret 泄露 | 永不进前端 |
| 原子 pop | 并发双换（一次授权两个会话） | Redis `DEL` 返回值 |

**两个设计决策值得记录**：

**(1) 一次性票据，token 永不进 URL。**

回调后不能把 access_token 拼在 URL 里返回前端——它会进浏览器历史、进 Referer、进服务端 access log。所以用 `?sso_ticket=`：

```
票据 60 秒有效、换过即废、不含任何身份信息
```

拿到票据也必须立刻来换，且换过就失效。这样即使票据泄露，损失窗口也只有 60 秒且大概率已被消费。

**(2) 身份以 userinfo 为准，本地不做签名验签。**

原实现要在本地验 ID Token 签名，但自研验签是高风险动作（`alg: none` 绕过、`kid` 混淆、JWKS 轮换）。改为：本地只做 nonce / aud / iss 的**非签名**解包，真正的身份取自 IdP 的 userinfo 端点——那是 IdP 直接返回的、走服务端到服务端 TLS 的可信数据。

**假 IdP 必须实现真校验**：验收脚本内置的假 IdP 会校验 `client_id` / `code_challenge`（PKCE SHA256）/ `redirect_uri` / code 一次性。如果假 IdP 什么都接受，那"客户端写错了"这类 bug 就永远测不出来。

还有一个反直觉的细节：**假 IdP 的 userinfo 绝不能返回 nonce / aud / iss**。因为代码里是 `identity.update(userinfo)`，返回这些字段会把真正的 nonce 覆盖成空值，让 nonce 校验凭空失效——一个"什么都返回"的假 IdP 会让这道防线永远显示绿色。

**验收**（95/95 + 24/24 真实链路）：

```
✅ 租户由 IdP claim 判定 = acme
✅ 角色由 groups 映射（rag-users → user）
✅ 票据复用被拒（一次性）   HTTP=401
✅ state / CSRF / nonce / aud / iss 五道防线逐一验证
✅ 禁用账号走 SSO 也无法登录
✅ 审计记录含 IdP 来源、不含 token 明文
```

**角色同步的取舍**：SSO 通过后，本地角色**以本地记录为准**，只在首次开户时用 IdP 的组映射结果。原因：IdP 的组反映岗位，本地角色反映知识库权限。每次登录都覆盖会让管理员在后台的调整被静默抹掉。

### 2.9 GB 级大文档流式处理（本轮新增，46/46）

**验收口径**：`verify_p4_bigfile.py` 在单次运行里真实生成一份 **1024MB** 文本，走"流式解析 → 流式切片 → 异步入库 → 检索"全链路。

**核心实测数据**（1024MB 文件，本机 15.7GB 内存）：

```
解析峰值内存 < 64MB（与文件大小无关）        峰值 19.4 MB / 文件 1084MB
流式片数与全量一致（语义等价，不是简化版）    流式 949407 / 全量 949407
流式峰值显著低于全量                         全量 4784.5 MB → 流式 26.1 MB（降 183.0x）
所有文本形态 × 块大小组合均逐字节一致         12/12
文件 ×2.1 → 临时开销 ×1.42（29.6 → 42.1 MB） ← 解耦的直接证据
处理过程临时开销是常数级（< 256MB）           临时 29.1 MB
按块读取（read 参数不是 -1）                  read 次数 1085，块大小 1048576
超限时提前终止读取（未读完整个文件）           已读 2.0 MB / 文件 8.3 MB
```

三条最值得说的：

1. **全量峰值 4784MB ≈ 文件 ×4.7**。这不是理论推算——同一份 1024MB 文件在同一台机器上，全量路径真的把 4.7GB 内存顶了出来。这就是"GB 级文档必须流式"的定量依据：内存需求与文件大小解耦，而不是"加内存条"。
2. **逐字节等价（12/12）**。流式切片若只保证"片数相同"，切点仍可能全部错开，检索表现会静默劣化。这里用 4 种文本形态 × 3 种块大小交叉对拍，每一片的内容都与全量完全一致。
3. **临时开销 ×1.42 < 文件 ×2.1**。文件翻倍、处理开销不跟着翻倍，这才是"解耦"的直接证据；单个规模的绝对值（29MB）可能只是常数碰巧小。

**逐字节等价是"语义等价"的前提**：片数相同 + 内容相同 → 向量相同 → 检索行为与全量路径完全一致。流式不是简化版。

### 2.10 K8s 部署与弹性扩容（本轮新增，46/46）

**验收口径**：`verify_k8s_manifests.py` 对 `k8s/` 下 8 个 YAML 做结构断言（不连集群），覆盖：

| 类别 | 校验点（摘要） |
|------|----------------|
| 探针语义 | liveness 只看进程存活（`/api/v1/health`）、readiness 查依赖（`/api/v1/ready`）、均不指向鉴权路径；worker 有 startupProbe（容忍 5 分钟冷启动） |
| 弹性扩容 | api HPA min<max 且带指标；KEDA ScaledObject 按 Redis list 长度伸缩、覆盖 `rag` 与 `rag_large` 两条队列、大文档阈值更灵敏 |
| 中断安全 | api ≥2 副本 + PDB（selector 能选中真实 Deployment）；worker `maxSurge: 0 / maxUnavailable: 1` |
| 资源与配置 | requests/limits 齐全、`terminationGracePeriod > timeout-graceful-shutdown`、selector 与 Pod label 匹配、不含真实密钥 |

**两个容易踩错的编排细节**（清单里已固化）：

- **worker 的滚动策略要反过来**：`maxSurge: 0`。大文档任务动辄跑十几分钟，若和 api 一样"先起新的再停旧的"，发布期间副本翻倍，抢同一队列导致任务重复调度。
- **没有 PDB 时 `kubectl drain` 会把 Pod 全部驱逐**：集群升级 = 全站中断一次，且不触发任何告警。PDB `minAvailable: 1` 保证滚动驱逐时至少有一个实例在服务。

## 四、本阶段修复的真实缺陷清单

按严重程度排序。**每一条都是"功能看起来正常"但实际有洞的类型**。

| # | 缺陷 | 后果 | 严重度 |
|---|------|------|--------|
| 1 | 审计表未写 `tenant_id` | B 租户管理员能看见 A 租户全部操作 | 高（跨租户泄露） |
| 2 | claims 租户非法时静默降级 | 用户被丢进默认租户，看到别人内容 | 高（静默串户） |
| 3 | `/login` 页面返回 401 | 登录页自己需要登录，形成死循环 | 高（功能不可用） |
| 4 | OIDC state 存进程内 | 多副本下登录随机失败 | 高（多副本不可用） |
| 5 | SSO 票据存进程内 | 多副本下换票失败，被踢回登录 | 高（多副本不可用） |
| 6 | 告警评估每副本各跑 | 重复告警 + 延迟告警 | 中（运维噪音） |
| 7 | `container_name` 写死 | 无法 `--scale`，多副本部署不了 | 中（阻塞部署） |
| 8 | 缺租户管理 API | 开租户要连数据库执行 SQL | 中（能力不可用） |
| 9 | 停机窗口 10s < 问答 120s | 在途请求被腰斩，502 但日志正常 | 中（难以排查） |
| 10 | 审计队列未落库即丢 | `kill -9` 时丢审计 | 低（已知限制） |
| 11 | 任务 payload 键名错配（接口写 `size`，worker 读 `file_size`） | `use_stream` 恒 False，**GB 级文件也走全量 read_bytes()**，流式链路形同未接 | 高（核心链路失效） |
| 12 | `_save` 用 `json.dumps` 全量序列化元数据 | GB 级语料下峰值比数据本身还大 1~2 倍，内存紧张时直接 MemoryError（崩在"写 64 字节"这种位置） | 高（GB 级不可用） |
| 13 | `_ensure_capacity` 前 `np.vstack` 整表复制 | 扩容峰值 ≈ 3 倍矩阵大小，GB 级语料必然 OOM | 高（GB 级不可用） |
| 14 | 离线向量用内置 `hash()` | `PYTHONHASHSEED` 随机化使同一文本在不同进程算出不同向量，**重启后旧向量全部错位**，检索静默劣化 | 高（数据损坏） |
| 15 | `np.load` 返回只读视图 | 进程重启后第一次原地写报 `assignment destination is read-only` | 中（仅重启后触发） |
| 16 | `_save` 依赖 `ensure_ready()` 建目录 | 空 PVC 首次入库 `FileNotFoundError`，报错位置像"磁盘故障" | 中（新环境不可用） |
| 17 | `np.savez` 内部 `tobytes()` 整块复制 | 落盘峰值再翻一倍；已改分块写裸 `.npy`（1024 行/块）+ mmap 读，实测额外峰值 0.0MB / 矩阵 78.1MB | 中（峰值翻倍） |
| 18 | 索引路径后缀歧义（`idx` 与 `idx.npy` 落在不同文件） | 配置写法一换，重启后"读到空索引但磁盘明明有数据" | 中（静默数据丢失） |
| 19 | `task_routes` 覆盖 `send_task(queue=...)` | 配置后大文档队列分流静默失效 | 中（分流失效） |
| 20 | KEDA 漏配 `rag_large` 队列 | 大文档任务堆积但 worker 不扩容 | 中（弹性失效） |
| 21 | api 缺 PDB | `kubectl drain` 全量驱逐，集群升级 = 全站中断且无告警 | 中（升级即中断） |
| 22 | worker 无 startupProbe、滚动策略未反向配置 | 冷启动被 liveness 误杀；发布期间副本翻倍抢队列 | 中（发布抖动） |

第 11 条最能说明问题：**功能测试全绿、接口全通，但流式链路从没被真正执行过**。键名错配不会报错，只是让 `use_stream` 永远为 False——直到用真实 1GB 文件端到端验证才现形。
第 1、2 条最能说明问题：**它们不会让任何功能报错**。系统看起来一切正常，租户隔离的测试也能过（因为测的是"能不能拦住"，而不是"拦住之后数据落在哪"）。这类缺陷只能靠"审计表里到底存了什么"这种较真才能发现。

第 11-22 条是 GB 级大文档与 K8s 轮次新增的。共同点：**在"小文件 + 单实例"的验证口径下全部绿灯**——`use_stream=False` 只是不启用优化、`np.vstack` 只是慢一点、缺 PDB 只是升级时会中断。验收口径升级到"GB 级文件 + 集群语义"后它们才现形。

## 六、已知限制与后续规划

诚实列出，不粉饰。

### 6.1 已知限制

| # | 限制 | 影响 | 为什么不现在做 |
|---|------|------|----------------|
| 1 | 审计队列在 `kill -9` 时丢未落库记录 | 极端情况丢审计 | 需引入消息队列，属于架构级改动 |
| 2 | 告警锁释放非原子（GET+DEL 之间） | 极端情况一轮可能双评估 | 需 Lua 脚本，引入 EVAL 依赖 |
| 3 | L1 缓存不跨副本失效 | 改文档后最多 60 秒旧值 | 知识库场景可接受，非金融场景 |
| 4 | Redis 降级时限流额度变 N 倍 | 降级期间限流精度下降 | 降级已是异常态，优先保证可用 |
| 5 | 前端零构建，无组件复用机制 | 代码组织靠纪律 | 规模可控，权衡后选择 |
| 6 | 单机 ES，无副本 | ES 挂了日志断流 | 演示规模足够，生产应接云 ES |
| 7 | 大文档内存量化依赖子进程，低内存机器上相关断言记 SKIP | SKIP 不是 FAIL，但要看清"这几条没测到" | HWM 是进程生命周期峰值，同进程增量恒为 0（见验证脚本 `measure_rss_in_child` 注释）；本机 15.7GB 可提交内存吃紧时脚本自动降级，**宁可 SKIP 也不给假数字** |
| 8 | 本地向量库改为裸 `.npy` 后，旧 `.npz` 索引不兼容 | 旧索引加载失败记 warning、从空开始（不会读进错误数据） | 本地向量库是无数据库环境的兜底实现；生产走 Qdrant，不受影响 |

### 6.2 后续可做

- **审计写入走 Celery**：解决限制 1，同时让审计写入不阻塞业务。
- **前端骨架屏 + 虚拟滚动**：文档上万条时的列表性能。
- **检索侧的 query 改写**：多轮对话里"它"指代上一轮实体，当前未做指代消解。
- **租户级资源配额限流**：当前 `max_qps` 字段已存在但未真正接入限流器。
